# 可观测性、审计与告警规范

> 状态：实施基线  
> 目标：所有数据链路可监控、可定位、可回放；所有 `WARN`、`ERROR`、`CRITICAL` 均有结构化日志和企微机器人可靠投递证据。  
> 性能原则：采集与通知不得在 SDK callback、`InsertOrder`/`CancelOrder` 调用或 journal 提交临界区执行网络 I/O。
> 服务范围：覆盖策略交易信号、全部 EMT 交易/账户操作与查询、全部原生交易/账户回调及恢复/对账；本项目没有行情链路、行情指标或行情告警。

## 1. 术语与不变量

| 术语 | 定义 |
| --- | --- |
| `TraceContext` | 由 `trace_id`、`span_id`、`correlation_id`、`command_id` 和载荷哈希组成的链路关联上下文。 |
| `FlowRecord` | 记录数据在一个确定边界的输入、输出、结果和时间的审计记录。 |
| `AuditLedger` | `FlowRecord` 的追加式、可校验、可重建索引的事实账本。 |
| `AlertOutbox` | `WARN+` 告警的持久化待投递队列，保存企微投递尝试与结果。 |
| `alert_id` | 一条原始告警的稳定 UUID；告警批量、日志、企微内容和 Ops 查询均以它关联。 |
| `WARN+` | `WARN`、`ERROR`、`CRITICAL` 的统称。 |

必须始终满足：

1. 任意业务命令、原生调用、回调、投递、内部恢复/对账查询、配置变更和人工状态变更都可由 `correlation_id` 关联到完整审计路径。
2. 每一条 WARN+ 都有一个 JSON 日志事件和一个已持久化的 `AlertOutbox` 条目；任何一者失败都是新的 Critical 可观测性故障。
3. 企微机器人仅是通知通道，不是告警事实源。通知失败不得覆盖、删除或降低原始严重度。
4. AuditLedger、Command Journal、Event Journal 的原始分段均为只追加恢复证据；查询索引、指标库、trace 后端和日志聚合器均可重建。
5. 审计记录的丢失、无法入队、校验链断裂、时间戳不可用或关联字段缺失都必须 fail-closed：停止新订单并转入 `RECONCILE_REQUIRED`。

## 2. 数据链路覆盖矩阵

| 链路边界 | 必须记录的 FlowRecord | 必要指标 | 关联键 |
| --- | --- | --- |
| 策略连接 → Ingress | 认证结果、协议版本、帧接收、拒绝原因、载荷哈希。 | 活跃连接、帧率、帧错误、认证失败。 | `connection_id`、`strategy_slot`、`trace_id`。 |
| Ingress → 风控/幂等 | 快照版本、规则结论、额度前后值、幂等命中/冲突。 | 接收/拒绝率、策略配额、快照年龄。 | `command_id`、`client_order_id`、`policy_version`。 |
| 风控 → Command Journal | `COMMAND_PREPARED` LSN、持久化结果、批次 ID、耗时。 | fsync 延迟、批量大小、写入错误、磁盘空间。 | `command_id`、LSN、payload hash。 |
| Journal → EmitShard → EMT | 选定 shard、`CALL_STARTED`、SDK 调用起止、返回值/异常、`order_emt_id`。 | 调用 p50/p99/p99.9、发送失败、柜台流控。 | `command_id`、`order_client_id`、`order_emt_id`、`session_epoch`。 |
| EMT SPI → callback ring | callback 类型、入队结果、ring 序号、水位、最小字段 hash。 | 回调率、入队耗时、ring 水位/溢出。 | `session_epoch`、原生 ID、`trace_id?`。 |
| Normalizer → Event Journal | 归属规则、去重结论、`event_id`、事件 LSN、状态变迁。 | 未归属/重复事件、normalize 延迟、落盘失败。 | `event_id`、原生 ID、`command_id`。 |
| Event → 投影/客户端 | projection 版本、`delivery_id`、批量、ACK、重放。 | 投递延迟、ACK 延迟、积压、慢策略。 | `event_id`、`delivery_id`、`strategy_slot`。 |
| 内部恢复/对账查询 | `request_id`、分页、`is_last`、来源、差异结论。 | 查询延迟、超时、页数、差异数。 | `session_epoch`、`request_id`、`correlation_id`。 |
| 配置/人工控制 | 发起身份、审批/变更单、前后配置 hash、状态转换。 | 变更次数、未审批尝试。 | `correlation_id`、审计 actor、配置版本。 |
| WARN+ → 日志/通知 | `alert_id`、指纹、日志偏移、outbox LSN、每次投递结果。 | 告警率、outbox 积压、企微送达/失败/重试。 | `alert_id`、`correlation_id`、`trace_id`。 |

SPI callback 本身只有最小 native 字段，可能尚不能获得完整 TraceContext。Normalizer 必须用交易日、会话、`order_emt_id`、`order_client_id` 和命令映射补链；不能补链的事件标为 `UNATTRIBUTED_NATIVE_EVENT` 并进入对账，绝不能伪造 `trace_id` 或猜测策略归属。

## 3. 审计记录与完整性

### 3.1 `FlowRecord` 最小字段

```text
record_version, record_id, parent_record_id,
trace_id, span_id, correlation_id, command_id,
trading_day, session_epoch, account_alias, strategy_slot,
stage, operation, direction, outcome, native_code, error_fingerprint,
input_payload_hash, output_payload_hash,
command_lsn, event_lsn, audit_lsn,
order_client_id, order_emt_id, event_id, delivery_id,
monotonic_ns, observed_at_ns, prev_record_hash, record_hash
```

- `account_alias` 为不可逆、非真实账号的部署别名；不得使用真实账户、密码、Token、企微 webhook 或完整订单载荷。
- `payload_hash` 基于规范化二进制载荷，明确版本和哈希算法。哈希用于证明输入/输出一致性，不能作为敏感数据加密或替代持久化业务事实。
- `prev_record_hash` 与 `record_hash` 在每个审计分段内形成链；段末写 checkpoint、段 hash、签名/密钥版本（若启用）。
- 每段记录开始/结束 LSN、创建/关闭时间、应用版本、SDK capability report hash 和配置版本。恢复时仅承认连续 CRC、commit marker 与哈希链均有效的前缀。

### 3.2 写入与故障语义

1. 热路径生成定长或紧凑二进制 `FlowRecord` 并交给预分配有界队列；callback 只记录最小 callback 观察，不执行 JSON、磁盘、HTTP 或企微调用。
2. Audit writer 批量追加、写入 commit marker 后，异步生成 JSON 日志、trace export 和指标。命令/事件 Journal 的 LSN 是优先恢复依据，AuditLedger 可以由其重建索引。
3. `WARN+` 不能仅存在内存：AlertOutbox 与对应日志引用必须在确认告警创建前持久化。Outbox 写入失败、审计队列硬满、日志 writer 不可用、哈希链错误或时钟/磁盘异常均触发 Critical，并停止新订单。
4. 索引、trace exporter、日志聚合器或企微网络异常可以重试；它们不能回压 SPI callback 或令已开始的 SDK 调用重试。若到达本规范的 Critical SLA，则由状态机停止新订单。

## 4. 结构化日志

### 4.1 格式与最低字段

应用日志采用 UTF-8 JSON Lines，一条事件一行。`INFO` 可按性能策略异步批量写入；WARN+ 由专用 writer 追加并与 `AlertOutbox` 关联。最低字段：

```json
{
  "ts": "2026-08-25T09:30:00.123456789+08:00",
  "level": "ERROR",
  "event": "native.insert_order.exception",
  "alert_id": "01J...",
  "correlation_id": "...",
  "trace_id": "...",
  "command_id": "...",
  "account_alias": "acct-a",
  "trading_day": "YYYYMMDD",
  "session_epoch": 42,
  "error_fingerprint": "...",
  "native_code": null,
  "audit_lsn": 123456,
  "message": "脱敏摘要"
}
```

`message` 只用于人读摘要，程序必须使用稳定的 `event`、`level`、`error_fingerprint`、ID 与枚举字段。日志轮转不跨交易日打乱时间排序；每个归档文件附带 hash、LSN 范围、保留期和完整性检查结果。

### 4.2 禁止写入

- EMT 登录密码、策略 Token、连接会话密钥、企微 webhook/密钥、私钥、完整账号或身份证明；
- 原生结构体的全量 `repr`、未经批准的订单备注、客户端自带的不可信异常堆栈；
- 能由载荷 hash、受控 ID、脱敏代码替代的完整订单/成交个人数据。

异常堆栈可写入受限诊断存储，但仍必须脱敏、设置访问权限和保留期；普通日志与企微只引用 `correlation_id`。

## 5. 指标、trace 与只读查询

### 5.1 必要指标

指标使用低基数 label（`account_alias`、`strategy_slot`、`operation`、`outcome`、`severity`），禁止将订单号、symbol、`trace_id`、错误文本作为 label。

- 交易：命令接收/拒绝/调用/原生接受/未知提交数量，柜台流控、撤单和未决数量；
- 延迟：五段端到端直方图、journal/AuditLedger durable 延迟、SDK 调用、callback 入队、事件投递和 ACK；
- 队列：Ingress、EmitShard、callback ring、Audit、Event、AlertOutbox 的长度、水位、最老年龄、drain rate；
- 完整性：LSN/哈希链检查、审计缺口、未归属回报、对账差异、丢弃/拒绝计数；
- 通知：WARN+/ERROR/CRITICAL 生成量、outbox backlog、企微发送成功率、重试次数、最大送达延迟、未送达 Critical 数。

### 5.2 trace 与 Ops

trace 导出采用 OpenTelemetry 兼容数据模型，但本地 AuditLedger 是权威链路证据。导出不可用只影响外部可视化，不得丢弃原始审计记录。

Ops 仅提供经过本机认证的只读查询，例如：

```text
GET /ops/v1/traces/{correlation_id}
GET /ops/v1/alerts/{alert_id}
GET /ops/v1/commands/{command_id}
GET /ops/v1/health/observability
```

查询响应只返回脱敏摘要、状态、LSN、时间、关联 ID 和经授权的审计引用。查询本身也生成 `FlowRecord`；Ops 不提供直接“已处理”“忽略告警”“重发订单”按钮。

## 6. 告警分类与企微投递

| 等级 | 示例 | 日志 | AlertOutbox/企微 | 交易动作 |
| --- | --- | --- | --- |
| `INFO` | 正常登录、查询完成、配置已应用。 | 必须。 | 默认不发。 | 无。 |
| `WARN` | 策略慢、队列高水位、流控、查询超时、通知重试。 | 必须。 | 必须，允许同指纹短窗口批量。 | 限制受影响能力；按规则升级。 |
| `ERROR` | SDK 调用异常、会话断线、journal 单次失败、策略投递失败。 | 必须。 | 必须，持久化后至少一次发送。 | 关闭相关路径；通常 `DEGRADED` 或 `RECONCILING`。 |
| `CRITICAL` | 审计缺口、callback 溢出、持久化失败、未解释提交、Critical 通知超 SLA。 | 必须。 | 必须，最高优先级；不能与低级别告警混批。 | `DISARMED` 或 `RECONCILE_REQUIRED`，停止新订单。 |

### 6.1 AlertOutbox 状态机

```text
CREATED → PERSISTED → READY_TO_SEND → SENDING
  → DELIVERED
  → RETRY_SCHEDULED → READY_TO_SEND
  → ESCALATED_UNDELIVERED
```

- 只有企微响应被验证为成功后才进入 `DELIVERED`。进程在 `SENDING` 崩溃时恢复为待投递，因此语义为至少一次，允许重复送达。
- 网络错误、超时、限流及可重试服务端错误使用带 jitter 的指数退避；`alert_id` 贯穿每次尝试。不可重试响应仍保留证据并进入 `ESCALATED_UNDELIVERED`，由运维修复配置后重新投递。
- 同一指纹的告警可以在有限窗口合并为一条企微消息；消息必须列出严重度、账户别名、发生区间、总数、`alert_id` 列表或连续范围、首个 `correlation_id` 和本机 Ops 查询提示。每条原始 outbox 记录仍独立保留并标明所在批次。
- 企微 payload 只使用脱敏模板，长度受配置上限约束；超长上下文以 `correlation_id`/`alert_id` 引用，不截断 ID、不传递敏感正文。

### 6.2 通知失败的升级策略

1. 每次失败写 WARN+ 日志并更新 Outbox 尝试记录，保留企微返回码分类但不得记录 webhook。
2. Outbox 的年龄、数量、重试次数、Critical 未送达时间均为监控指标；超过 Warning/ Critical 阈值生成新的告警，形成可追溯的“告警通道故障”链。
3. 若任一 Critical 告警超过 `critical_delivery_sla_seconds` 未送达，网关按账户配置进入或保持 `DISARMED`；已 `CALL_STARTED` 的订单继续对账，不会重发。
4. 企微恢复后优先投递最旧的 Critical，再投递 Error/Warn；不因恢复而清空历史或降低严重度。

## 7. 留存、权限与审计复核

- Command/Event/Audit Ledger、AlertOutbox、结构化 WARN+ 日志和企微投递回执的保留期由风控定义，不得短于订单争议、对账和监管审计所需期限；具体天数通过生产配置/制度确定。
- 删除/归档仅由受控作业在完整性验证、备份验证和保留期到期后执行，操作本身写入 AuditLedger 和企微通知。未归档、未校验或有关联未决订单的段禁止删除。
- 运行账户只能追加；审计查询、日志查看、告警配置和密钥管理按最小权限分离。企微 webhook 只能由 notifier 进程经 `SecretProvider` 读取。
- 每日执行账本/日志 hash 验证、AlertOutbox 未送达扫描和随机 trace 回放；每次发布、日切和故障恢复必须保存审计完整性结论。
