# 运维与故障处置手册

> 本手册只授权观察、停止新单、对账和经审批恢复。它不授权修改原生订单、删除日志、自动重报或绕过风控。

## 1. 服务状态

| 状态 | 新订单 | 含义与动作 |
| --- | --- | --- |
| `BOOTSTRAP` | 拒绝 | 读取配置、校验权限和 journal。 |
| `LOGINNING` | 拒绝 | 初始化 SDK 并登录。 |
| `REPLAYING_PUBLIC_FLOW` | 拒绝 | 接收本交易日公共订单/成交流。 |
| `RECONCILING` | 拒绝 | 合并日志、公共流和仅供恢复/对账的异步查询。 |
| `DISARMED` | 拒绝 | 会话健康但等待风险快照、人工审批或故障解除。 |
| `READY` | 允许 | 满足会话、对账、策略和队列健康条件。 |
| `DEGRADED` | 通常拒绝 | 限流、慢策略或非关键依赖异常；按告警规则升级。 |
| `RECONCILE_REQUIRED` | 拒绝 | 原生副作用/回调事实不完整，必须完成对账。 |
| `STOPPING` | 拒绝 | 关闭新单、排空受控工作并持久化 checkpoint。 |

状态迁移必须写入 Event Journal，附带原因、操作者/控制面版本和相关 LSN。只读 Ops 接口允许查看状态，敏感状态切换仅经本机受认证控制管道执行。

## 2. 必看指标与告警

| 信号 | 告警级别 | 立即动作 |
| --- | --- | --- |
| 登录失败、SDK 断线、服务端重启 | Critical | 切 `RECONCILE_REQUIRED`，停止新单，执行重连与对账。 |
| callback ring 达硬水位/溢出 | Critical | `DISARMED`，保存证据，全量订单/成交对账。 |
| journal/audit ledger flush 失败或超时、剩余空间不足 | Critical | 停止新单；保护命令、事件与审计证据，不要重启覆盖。 |
| 未解释 `SUBMIT_UNKNOWN`、订单映射冲突 | Critical | 禁止恢复交易，核查原生订单/成交。 |
| `211008` 或流控显著上升 | Warning | 收缩发射窗口，确认策略未绕过退避。 |
| 策略快照过期/策略 ACK 超时 | Warning | 关闭受影响策略或全局新单，检查控制面/客户端。 |
| queue 高水位、p99.9 持续恶化 | Warning | 先停内部查询和慢策略，必要时 `DISARMED`。 |
| 未归属原生事件 | Warning | 记录并对账；不得按标的/时间猜测归属。 |
| `AlertOutbox` 积压、企微失败率或通知延迟超过 SLA | Warning/Critical | 验证 webhook/网络/限流；保留 outbox 并重试。Critical 未送达按配置维持或切换为 `DISARMED`。 |
| trace/审计哈希链断裂、FlowRecord 队列满 | Critical | 记录链路缺口，进入 `RECONCILE_REQUIRED`，禁止通过采样或清理队列恢复。 |

## 3. 标准故障处置

### 断线、登录失败或服务器重启

1. 确认服务已停止接收新订单，记录当前 `session_epoch`、交易日、未决命令数和队列水位。
2. 保留 journal、SDK 日志和指标快照；不要清空队列或重启策略以制造新的订单。
3. 按生命周期线程执行 `Logout → Login`，并在登录前重新完成 SPI 注册、公共流订阅、心跳和版本设置。
4. 接收公共流重传，依次发起未完成订单、订单分页、成交分页、资金和持仓查询。
5. 合并结果，解释所有 `CALL_STARTED`、未归属事件和映射差异；仍有差异则保持 `RECONCILE_REQUIRED` 并升级风控/券商支持。
6. 对账完整且风险快照有效后，经审批转为 `READY`。

### callback ring 溢出

1. 立即停止新订单和非必要内部查询，切至 `RECONCILE_REQUIRED`；记录 ring 容量、水位、生产/消费速率和线程栈。
2. 不尝试“丢掉旧事件恢复速度”。保留溢出前后 journal 段和 SDK 日志。
3. 重建会话，使用公共流重传与查询做全量对账；验证策略 delivery 游标。
4. 根因修复须经压测复现（容量、消费性能、慢策略隔离、SDK callback 行为），再逐步恢复。

### journal 异常或磁盘空间不足

1. 关闭交易闸门，禁止新的 `InsertOrder` 与 `CancelOrder`；保持已提交命令的恢复证据。
2. 执行只读完整性检查：连续 LSN、CRC、commit marker、磁盘错误和可用空间。
3. 通过扩容/切换经批准的数据盘恢复空间，不能删除未归档 journal；仅在备份验证后按保留策略清理完整历史段。
4. 恢复时只截断无效尾部，重建投影并对账；未证明完整前不可 `READY`。

### 柜台流控

1. 记录原生错误、当前令牌窗口、队列、策略来源与时间窗口。
2. 维持自适应控制器的乘性收缩和冷却，不得增加 emitter 线程或让策略换 ID 重报。
3. 优先保证已发订单的撤单、回报处理和对账；按审批后的速率逐渐增加新订单配额。
4. 若持续触发，核查券商限额、账户状态和策略突发模型，必要时维持 `DEGRADED` 或 `DISARMED`。

### 企微机器人不可用或告警积压

1. 通过 `alert_id`、错误指纹和 `correlation_id` 确认原始 `WARN+` 已写入结构化日志和 AlertOutbox；通知失败不得被标记为已送达。
2. 检查 webhook secret 引用、DNS/网络、企微返回码、发送速率和重试退避。Webhook 及完整消息体不得输出到普通日志或截图。
3. 维持持久化 outbox 的至少一次重试；相同错误可批量通知但不能删除原始告警。恢复后允许重复消息，依 `alert_id` 去重。
4. 若 Critical 告警在配置 SLA 内未获得企微送达确认，按账户策略停止新单或保持 `DISARMED`，并通过预设的人工值班路径升级；在未记录审批理由前不得忽略该状态。

### 审计链缺口或 trace 查询不完整

1. 立即停止新订单，记录缺口的 `trace_id`、LSN 区间、队列水位、哈希/checkpoint 与所有受影响的业务 ID。
2. 保全 Command/Event/Audit Ledger、结构化日志和 AlertOutbox；不重建、删除或覆盖任何原始段。
3. 使用 command/event LSN 和原生查询重建 AuditLedger 索引，并核对回放结果；对无法证明完整性的订单维持 `RECONCILE_REQUIRED`。
4. 根因解决（容量、磁盘、权限、消费者性能或版本兼容）并完成故障回归后，经审批恢复交易。

## 4. 对账清单

以 `GetTradingDay()` 为边界，对每个账户比较：

- Command Journal 中的 `COMMAND_PREPARED`、`CALL_STARTED`、`NATIVE_ACCEPTED` 与本交易日原生订单；
- `order_client_id`、`order_emt_id`、账户、`client_id` 与策略归属映射；
- 原生成交与 Event Journal / 客户端 ACK 游标；自成交必须按复合键核对；
- 订单数量、冻结/可用资金、持仓与已知成交的变化；
- 未归属回报、迟到回调、分页/查询失败和所有人工处置记录。
- 每个 `WARN+` 的 `alert_id`、结构化日志位置、outbox 状态、企微尝试/送达时间，以及无法送达时的人工升级记录。

对账结论只能是“完整一致”“存在可解释差异”或“未解释差异”。最后一种必须保持不可交易并升级；不能因为市场收盘或服务超时而自动视为一致。

## 5. 日切与变更操作

- 日切前：冻结新单，核对未决订单，归档完成段并校验 restore/read，记录 SDK、配置和 capability report 版本。
- 日切后：新建 API、登录、重传、查询、对账，在 `DISARMED` 等待策略快照和审批；不用本机零点判断交易日。
- 应用/SDK/配置升级：先做只读演练，再按部署文档灰度。SDK、`client_id`、持久化参数和路径的变更均视为高风险变更。
- 严禁：删除 journal 修复告警、在同一账户/client_id 启动第二活跃实例、通过重启跳过对账、使用全撤替代映射恢复。
