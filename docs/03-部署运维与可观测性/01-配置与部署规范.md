# 配置与部署规范

> 本文定义 Linux x86_64 上单账户单实例的安全部署。Windows 不属于支持、验收或发布范围。所有值均为示例，账户、密码、Token、IP 和真实路径不得提交到仓库。

## 1. 平台前提

| 项目 | Linux x86_64 |
| --- | --- |
| Python 与 `.venv` | 每个部署根目录使用独立且不提交的 64 位 CPython 3.10 `.venv`；不得因其他版本可导入而放宽生产基线。 |
| EMT SDK | 使用供应方交付、与发行版、glibc、架构和 Python ABI 匹配的 `.so` 及依赖；仅为服务进程设置 `LD_LIBRARY_PATH`。 |
| 服务方式 | 专用非登录用户 + `systemd`，服务重启后保持 `RECONCILE_REQUIRED`。 |
| 持久化确认 | `fdatasync` 或 `fsync` 成功。 |
| 终端信息 | EMT FAQ 提示登录会采集终端信息；安装 `lshw` 并向服务用户仅授予该程序的最小执行权限。 |

Linux 支持以实际供应包为准。上线前在目标机器执行 `ldd`、Python 导入、创建 API、登录、回调和查询 P0 探针；不得只因系统存在 Linux 终端枚举就认定 binding 可用。业务代码只能通过 `native_api.py` facade 访问 SDK；完整契约及当前供应包限制见[Linux运行环境与SDK兼容性](./02-Linux运行环境与SDK兼容性.md)。

## 2. 目录、身份与权限

每个账户独立根目录，例如：

```text
<gateway-root>/
  .venv/                  # 当前 Linux 实例专属；不提交
  emt_gateway/            # 业务代码
  bin/                    # 只读应用与已审核 SDK
  config/                 # 只读配置；密钥由服务账户读取
  data/<account-alias>/
    command-journal/
    event-journal/
    audit-ledger/
    alert-outbox/
    # 订单/成交投影持久化至专用 PostgreSQL schema；本地不保存订单投影库
    checkpoints/
    emt-sdk-log/
  run/<account-alias>/    # PID/本机控制 socket
  logs/                   # 应用日志，不含密钥和完整原生载荷
```

- `data/<account-alias>` 不能被其他账户实例共享；账户别名不得包含真实账号。
- 运行账户仅可读 `bin/`、`config/`，并对自身 `data/`、`run/`、`logs/` 可写；普通用户和网络共享均无写权限。
- 进程监听 `127.0.0.1` 的策略端口和 Ops 端口；`nftables` 仍需显式拒绝外部访问。
- 使用操作系统密钥库、受控 secret store 或 ACL 严格的密钥文件；禁止把密钥放入命令行、环境变量转储、崩溃包或 journal。
- `audit-ledger/` 和 `alert-outbox/` 与订单 journal 同属恢复证据，不能被日志轮转程序删除；普通应用日志可按保留策略轮转，但必须先确保对应审计/告警证据已归档。

## 3. Linux `lshw` 最小权限示例

先确认真实路径：`command -v lshw`。由管理员使用 `visudo` 配置仅允许运行账户执行该绝对路径，例如：

```sudoers
emtgateway ALL=(root) NOPASSWD: /usr/sbin/lshw
```

路径必须以实际 `command -v lshw` 结果为准。不得配置 `NOPASSWD: ALL`。配置后以服务用户运行一次受控登录探针并保留脱敏结论。

## 4. 配置模型

配置文件使用 YAML 或 TOML；加载后转换为不可变 `RuntimeConfig`，启动时做 schema、路径、权限和连通性校验。示例：

```yaml
instance:
  account_alias: acct-a
  bind_host: 127.0.0.1
  dataplane_port: 18701
  ops_port: 18702
  platform: auto
emt:
  client_id: 7
  software_version: emt-gateway/0.5
  heartbeat_seconds: 10
  public_topic: restart
  sdk_home: /opt/emt/sdk  # Linux SDK：vendor/emt/linux-x86_64
  sdk_log_dir: /var/lib/emt-gateway/acct-a/emt-sdk-log
journal:
  durability: micro_batch       # strict | micro_batch
  max_batch_records: 32
  max_commit_wait_us: 500
  segment_bytes: 268435456
queues:
  ingress_items: 8192
  emit_items_per_shard: 4096
  callback_ring_items: 65536
  high_watermark_ratio: 0.70
  hard_watermark_ratio: 0.90
risk:
  policy_ttl_seconds: 30
  max_open_orders: 100
  reject_on_snapshot_stale: true
capabilities:
  emt_api_catalog_version: 2.27.0
  require_runtime_api_version_match: true
  require_full_callback_catalog: true
  require_explicit_account_operation_grant: true
  require_explicit_account_query_grant: true
observability:
  audit_durability: micro_batch
  audit_max_commit_wait_us: 1000
  trace_export_enabled: true
  structured_log_path: /var/log/emt-gateway/acct-a.jsonl
  warn_error_log_sync: true
alerting:
  warn_enabled: true
  error_enabled: true
  critical_delivery_sla_seconds: 60
  wecom:
    enabled: true
    webhook_secret_ref: secret://emt-gateway/acct-a/wecom-webhook
    max_batch_alerts: 20
    initial_retry_seconds: 1
    max_retry_seconds: 300
```

生产配置不包含 `password`、策略 Token、企微 Webhook 或私钥。它们通过 `SecretProvider` 在进程启动后读取，构建 EMT API 后立即清理可变缓冲区。`capabilities` 的 catalog 版本必须与 capability report 和 [全覆盖矩阵](../02-接口与数据/02-EMT交易与账户接口全覆盖矩阵.md) 一致；启用 `require_runtime_api_version_match` 时，Python binding 的 `GetApiVersion()` 结果必须匹配此基线，否则服务保持 `CAPABILITY_MISMATCH` 并拒绝交易。capability report 还必须记录 binding 文件 SHA-256、Python ABI、操作系统和架构。账户操作/查询默认拒绝，只有账户已开通且策略得到细粒度授权后才可启用。生产配置校验必须拒绝 `warn_enabled=false` 或 `error_enabled=false`；企微服务异常只能导致 outbox 重试/升级，不能通过关闭告警开关规避。任何配置变更生成审计记录；涉及账户、`client_id`、SDK 路径、日志/审计/告警目录、端口、持久化、通知或 capability 策略的变更必须重启且重新对账。

## 5. 启动与日常生命周期

### 启动前检查

1. 确认本交易日无同账户/`client_id` 活跃实例；确认端口、SDK 日志目录和 journal 目录均未被其他进程占用。
2. 验证 `.venv` 的 CPython 3.10 x86_64、密钥文件权限、journal 磁盘空间、磁盘 flush 基线、系统时间同步、SDK 动态库依赖和能力报告版本；必须验证 `ldd` 将 `libemt_api.so` 解析到 `sdk_home`。
3. 验证策略权限快照已加载且未过期；未获得快照只可启动为 `DISARMED`。
4. `RegisterSpi`、`SubscribePublicTopic(RESTART)`、SDK 心跳和软件版本设置必须发生在 `Login` 前。
5. 对 AuditLedger、结构化日志、AlertOutbox 做可写和恢复检查；验证企微 webhook 可用性。企微不可用不阻塞启动，但必须生成可见告警，并按 `critical_delivery_sla_seconds` 的策略决定是否维持 `DISARMED`。

### 正常启动顺序

```text
BOOTSTRAP → SDK_READY → LOGINNING → REPLAYING_PUBLIC_FLOW
→ RECONCILING → DISARMED → READY
```

只有完成订单/成交公共流重传、未决命令对账、快照构建和风险快照验证后，人工或受控控制面才能将 `DISARMED` 切为 `READY`。

### 日切与断线

- `GetTradingDay()` 是唯一交易日边界。开盘前受控轮换：关闭新单、排空/对账、`Logout`、`Release`、归档、重新创建 API、登录和重传。
- `OnDisconnected`、服务端重启、SDK 失败、日志异常或 callback ring 溢出立即关闭新订单；断线恢复按 `Logout → Login → 公共流重传 → 查询对账` 执行。
- 操作系统/服务管理器可以重启进程，但进程启动后必须停在 `RECONCILING`，不能因“服务已启动”自动恢复下单。

## 6. systemd 示例

以下是结构示例，真实用户、路径和解释器必须按安装环境替换：

```ini
[Unit]
Description=EMT Gateway (acct-a)
After=network-online.target
Wants=network-online.target

[Service]
User=emtgateway
Group=emtgateway
WorkingDirectory=/opt/emt-gateway
Environment="LD_LIBRARY_PATH=/opt/emt-gateway/vendor/emt/linux-x86_64"
ExecStart=/opt/emt-gateway/.venv/bin/python -m emt_gateway --config /etc/emt-gateway/acct-a.yaml
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true
UMask=0077

[Install]
WantedBy=multi-user.target
```

`Restart=on-failure` 只负责拉起进程；它不授权恢复交易。若 SDK 依赖、`lshw` 或设备识别需要额外系统访问，应逐项放行并记录理由，不应盲目启用强隔离选项导致登录失败。

## 7. 发布与回滚

1. 停止接收新订单，等待已持久化队列排空；对未决订单和成交完成对账。
2. 归档 journal 段、checkpoint、capability report、配置版本和基线指标；校验归档可读。
3. 以新版本启动至 `DISARMED`，执行只读查询、回放和 P0 冒烟测试。
4. 由双人审批放开小额白名单策略；持续观察指标后逐步扩大。
5. 回滚只回滚应用二进制/配置，不回滚或删除 journal。若数据结构不兼容，保留旧 reader 或执行经演练的单向迁移。
