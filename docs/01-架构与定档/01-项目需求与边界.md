# 项目需求与边界

> 状态：实施基线  
> 适用版本：`emt-gateway v0.5`

## 1. 项目目标

建设一个面向东方财富证券 EMT `TraderApi` 的本机交易网关。它只为多个受控策略提供**低延迟交易信号下单/撤单**与**可靠订单、成交、撤单错误回调**，并提供可审计的持久化证据和可恢复的账户对账能力。

策略自行获得行情、计算信号、决定价格和数量；网关不订阅、不缓存、不转发行情，也不运行指标、K 线、选股或策略定时器。网关的核心目标是缩短并稳定“策略信号到 EMT `InsertOrder` 返回”以及“SPI 回调到策略 ACK”的路径，同时保持以下正确性：不重复报单、不静默丢失回报、不跨策略路由、不能在未知原生副作用下自动重发。

## 2. 范围

| 类别 | 本期包含 | 明确不包含 |
| --- | --- | --- |
| 账户边界 | 一个部署实例绑定一个 EMT 账户和一个活跃 `client_id` 会话。 | 同账户/同 `client_id` 双活、高可用自动切换。 |
| 交易与账户能力 | 覆盖 EMT `TraderApi` 全部交易/账户方法和 `TraderSpi` 全部回调；策略可按细粒度权限提交账户操作/查询并接收原生语义回调。 | 行情订阅/查询、K 线/逐笔/盘口缓存、指标计算或信号生成。 |
| 策略接入 | 高性能 loopback TCP v2；既有 WebSocket v1 仅兼容信号和回调。 | 对公网直接暴露交易端口、浏览器直接下单、把网关作为行情中转。 |
| 平台 | 仅 Linux x86_64；每个部署根目录独立使用不提交的 CPython 3.10 `.venv`。实际支持以供应商发放的 Linux Python binding、动态库和 Linux P0 验证为准。 | Windows、Docker 容器绕过券商 SDK 依赖、macOS；复制业务代码维护多套平台项目。 |
| 可靠性 | 命令/事件日志、PostgreSQL 可重建投影、重连和日切对账、至少一次事件投递。 | 恢复期间对 `CALL_STARTED` 命令自动重新下单。 |
| 运维 | 本机只读状态查询、指标、告警、人工受控的断路/对账/恢复。 | 远程未审计管理后台、自动放开风险闸门。 |

## 3. 关键业务规则

1. `client_order_id` 是策略生成的稳定幂等键。客户端重试必须原样复用；同一策略对同一键提交不同载荷，一律拒绝为 `IDEMPOTENCY_CONFLICT`。
2. 网关在命令日志持久化前绝不调用 EMT；一旦命令进入 `CALL_STARTED`，即使超时、崩溃或断连，也不得自动调用第二次 `InsertOrder`。
3. `InsertOrder` 返回的非零 `order_emt_id` 表示请求由 SDK 接受，不表示交易所受理、订单有效或成交；订单和成交事实只以 SPI 回调及对账结果为准。
4. 撤单只允许针对本网关已证明归属且已映射到 `order_emt_id` 的订单。不存在“全撤”“全平”或按代码/时间猜测撤单的接口。
5. 控制面策略权限、额度、标的白名单必须以带版本和 TTL 的不可变快照在 Ingress 生效；快照过期、策略被禁用、会话异常或回调流不健康时，停止新订单。
6. 回调、查询、策略投递和投影均可延迟，但不得阻塞 SDK SPI 回调；到达硬性水位时进入 `DISARMED` 并对账，不能静默丢弃。
7. 每条命令、原生调用、SPI 回调、状态变换、事件投递、客户端 ACK、查询和告警都必须有可关联的追踪/审计标识；审计链有缺口即进入不可交易状态，不能用“日志采样”掩盖。
8. 每一个 `WARN`、`ERROR`、`CRITICAL` 都必须写入结构化日志并创建持久化告警 outbox 记录；企微机器人以至少一次方式投递，投递失败可追溯、可重试、可告警。
9. 策略发送的是已完成决策的订单/撤单信号，或经授权的 EMT 账户操作/查询意图。网关只做权限、静态合约规则、额度/账户快照和幂等校验，不依赖实时行情推导信号、价格或下单时机；最终市场规则由 EMT/柜台裁决。
10. 全部 EMT 交易/账户接口的覆盖以 [接口全覆盖矩阵](../02-接口与数据/02-EMT交易与账户接口全覆盖矩阵.md) 为准。接口未开通、SDK binding 缺失或策略未获授权时必须明确拒绝并记录 capability，不得静默忽略。

## 4. 非功能性需求

| 维度 | 必要要求 |
| --- | --- |
| 延迟 | 以目标机器 P0/P4 实测 p50/p99/p99.9 为发布基线；禁止编造固定微秒承诺。分别统计接收、日志提交、SDK 调用、回调入队、事件持久化、客户端 ACK。 |
| 吞吐 | 高性能协议支持长连接、批量收发、二进制编码和分片发射；最终订单速率必须低于柜台实际流控阈值。 |
| 安全 | 默认仅 `127.0.0.1`；最小权限服务账号；账户密码、Token、会话密钥不入日志；配置和日志目录不可由普通用户写入。 |
| 可恢复 | 进程异常、系统重启、SDK 断线、日切、日志尾部损坏、回调溢出后均进入可审计的恢复/对账路径。 |
| 可观测 | 每个命令、原生 ID 映射、会话状态、策略投递、队列水位、流控与失败都有可关联的日志/指标。 |
| 可追溯与通知 | 全链路必须能由 `trace_id`/`correlation_id` 回放到命令、原生回报、状态与投递结果；每个告警/报错均有 JSON 日志和企微告警 outbox 证据，告警自身也受监控。 |
| 可测试 | EMT SDK 必须封装在唯一 facade 后；业务层可用 fake API 做确定性单元和故障测试。 |

## 5. 角色与职责

| 角色 | 职责 | 禁止行为 |
| --- | --- | --- |
| 策略客户端 | 生成稳定业务 ID、接收至少一次事件并去重、尊重反压。 | 绕过 Gateway 直连 EMT；自行假设订单已成交。 |
| Gateway | 校验、持久化、调用 SDK、归一化回调、对账、隔离策略。 | 对 `CALL_STARTED` 重报；在 callback 中进行 I/O。 |
| 控制面 | 下发策略权限和额度快照，记录变更审计。 | 在订单热路径同步参与每笔决策。 |
| 运维/风控 | 配置账户环境、观察告警、受控解除闸门。 | 未完成对账即恢复交易；以删除日志方式清除故障。 |
| 券商/SDK 供应方 | 提供账户权限、白名单、SDK 和版本说明。 | — |

## 6. 上线前必须确认

1. 目标账户已开通所需市场、品种、交易权限和终端/IP 白名单。
2. 已取得与目标 OS、架构、Python ABI 匹配的 EMT Python binding 与原生库，并完成 P0 capability report。
3. 账户、`client_id`、部署实例、日志目录和策略密钥一一对应；无其他进程使用该会话。
4. 风险限额、白名单、订单价格/数量校验和人工熔断责任人已明确。
5. 已在非生产环境通过订单、撤单、断线、日切、杀进程、磁盘失败和回调溢出演练。
