# R1 发布与故障演练准备手册

> 状态：**2026-09-11 已在冻结 revision `75fa900` 的 Linux EMT 模拟盘窗口执行完 R1-A1--A6、Hot100、三轮 499 burst、OMS W7 与最终 query-only cleanup。** 各阶段的受控验收均通过；恢复结果严格保持 `RECOVERED_DISARMED`，`ready_claim=false`、`full_r1_acceptance=false`。本手册只组织非秘密发布物、Linux 演练输入、证据与失败边界；不加载 EMT SDK、不连接账户、不下单、不撤单，也不将账户提升为 `READY`。
>
> 当前权威范围见：[当前未实施功能与优化收口路线](./10-当前未实施功能与优化收口路线.md)。EMT native `last/is_last` 查询终态及三 scope 的精确关联 `RESTART` callback 已实证；本轮将这些子证据纳入 A/B 同账户、R2 强杀、负例和人工清理的统一窗口。证书仍不把有限的精确见证外推为任意历史订单的 callback replay 承诺，因此任何恢复结论仍必须是 `RECOVERY_BLOCKED` 或最多 `RECOVERED_DISARMED`。

## 1. 目标与不可越过的边界

R1 要证明的是：同一 EMT 账户存在 A、B 两个独立 TradeCore 系统时，A 的 R2 故障恢复只能识别和重建 A 自己的订单；B 和 unknown namespace 的订单绝不被 A 投影、撤单、重发或计入 A 的 callback gap。

本轮准备允许的动作仅为：生成/验证非秘密 release、校验 Linux 工具与输入路径、生成脱敏演练计划和运行静态质量门禁。下列动作只允许在 R1 统一演练窗口内、按对应 A 项执行：真实 EMT 登录、查询、受控委托、强杀、恢复或限速清理。

```text
离线发布控制面 ──签名 namespace release──> Linux 运行时预检
                                            │
                                            ├─ A1：静态质量与 release 合同
                                            ├─ A2：A/B 正常同账户组合
                                            ├─ A3：A 的 R2 强杀，B 保持
                                            ├─ A4：伪造/过期/冲突/unknown 负例
                                            ├─ A5：分页/中断/gap/负确认失败闭合
                                            └─ A6：人工批准后仅清理 A 的 own 订单

任一查询完成证书、回放、namespace、route 或 callback gap 不完整
    └─> RECOVERY_BLOCKED / DISARMED；零自动重报、零自动撤单、零 READY
```

## 2. 发布物包与存放规则

每个 EMT scope 使用独立的公开 release 包；私钥绝不进入 Git、运行目录、Journal 或 evidence。推荐的受限目录布局如下，目录名只使用逻辑 scope，不能包含真实账户、地址、口令或订单标识：

```text
<restricted-control-root>/r1/<trading-day>/<logical-scope>/
  namespace-release-v1.json          # 已签名；公开、不可原地覆盖
  namespace-trust-v1.json            # 公钥与撤销 signer ID；公开
  bootstrap-approval.json            # 首次激活的审批 ID/操作者/时间；无私钥
  release-state-v1.json              # 运行时原子状态；0600，不进入 Git
  evidence/                          # 仅脱敏 JSON/摘要/哈希
```

`namespace-release-v1.json` 必须包含并绑定：逻辑账户、交易日、`emt_client_id`、own/foreign 的不重叠 `order_client_id` 区间、owner、adapter instance、release epoch、运行代码 hash、信任锚 hash、有效期、证书与撤销引用、所有 lease 签名及 envelope 签名。epoch 升级时 successor 的 own range 必须严格位于已持久化 high-watermark 之后；任何已 checkpoint 的旧 own ID 不得重新归为 own，必须由新 release 以 foreign/retired 范围覆盖或在 SDK/session 前拒绝激活。

`namespace-trust-v1.json` 的最小公开格式为：

```json
{
  "schema_version": 1,
  "trusted_public_keys": [
    {"signer_id": "release-signer-id", "public_key_b64": "32-byte-ed25519-public-key"}
  ],
  "revoked_signer_ids": []
}
```

它只容纳 Ed25519 **公钥**。任何私钥字段、口令、SSH 字段或账户凭据出现时，预检必须失败并停止发布。

## 3. 演练前的静态准备

### 3.1 代码与工具

冻结候选 revision 后，在项目 `.venv` 中执行静态门禁，再复制 Git revision 到 Linux checkout：

```text
ruff check xuanling_tradecore emt_gateway tests tools
ruff format --check xuanling_tradecore emt_gateway tests tools
pyright
pytest -q
git diff --check
```

Linux 演练只允许使用 Git checkout；禁止上传源码覆盖运行目录。需要存在且可执行的工具为：

- `tools/acceptance/f2_controlled_execution_cycle.py`：单系统受控循环与现有 R1 权威扫描候选；
- `tools/acceptance/r1_dual_system_cycle.py`：A/B 组合编排；
- `tools/acceptance/r1_namespace_release_material.py`：离线构建 strict public trust，并用受限私钥签出不可覆盖的 R1 release；
- `tools/acceptance/r1_r2_crash_boundary.py`：在隔离 F2 子进程中验证真实 `InsertOrder()` 同步返回后、`NATIVE_ACCEPTED` 持久化前的 R2 `SIGKILL` 边界；
- `tools/performance/m3_emt_public_replay_probe.py`：仅公共流 `RESTART` 观察；
- `tools/acceptance/f1_mmap_physical_kill_drill.py`：不触碰 EMT 的本地 mmap 物理 kill 基线。
- `tools/acceptance/r1_release_preflight.py`：只验证公开 release/trust、scope、签名、runtime hash 与工具链，并生成脱敏 readiness evidence；不导入 SDK、读取账户文件或写 release state。

在 Linux 窗口前，先对每个逻辑 scope 执行一次 `r1_release_preflight.py`。它的 `prepared` 仅表示发布物和演练工具已就绪，不能替代 A1--A6，也不会解除 `RECOVERY_BLOCKED`。

命令必须从 Git checkout 的项目 `.venv` 以模块方式运行，路径均指向受限控制面中的**公开**文件：

```text
python -m tools.acceptance.r1_release_preflight \
  --namespace-release <restricted-control-root>/namespace-release-v1.json \
  --namespace-trust <restricted-control-root>/namespace-trust-v1.json \
  --expected-runtime-release-hash <sha256-of-reviewed-runtime-release> \
  --expected-account-id <logical-account-id> \
  --expected-trading-day <YYYY-MM-DD> \
  --expected-emt-client-id <scope-id> \
  --output <restricted-evidence-root>/r1-release-preflight.json
```

`expected-runtime-release-hash` 是绑定 Git checkout 的已审阅运行时发布物 SHA-256，Git revision 另行写入 evidence；它不是 Git 的短 SHA。`expected-account-id` 是已脱敏的逻辑 ID；命令行与报告中不得使用 EMT 真实账户号。预检拒绝覆盖既有 evidence 输出。

### 3.1.1 离线签名与 F2 外部 release 激活

将 public signer 与 revocation 文件转换为 R1 trust、再签出 release 的两个步骤均在受限发布控制面完成；私钥路径只传给第二步，不能复制到 Linux runtime、Git、Journal 或 evidence：

```text
python -m tools.acceptance.r1_namespace_release_material build-trust \
  --public-key <public-signer.json> \
  --revocations <public-revocations.json> \
  --output <restricted-control-root>/namespace-trust-v1.json

python -m tools.acceptance.r1_namespace_release_material sign-release \
  --request <reviewed-non-template-release-request.json> \
  --namespace-trust <restricted-control-root>/namespace-trust-v1.json \
  --private-keys <restricted-offline-private-key-file> \
  --output <restricted-control-root>/namespace-release-v1.json
```

`data/performance/config/emt/r1-namespace-release-request.template.json` 仅描述字段形状，`template=true` 会被 signer 拒绝。实际 request 必须由审核人填入逻辑 scope、own/foreign 无重叠区间、相同 EMT scope 对应的 adapter instance、有限有效期和已审阅运行时 SHA-256。

F2 的 R1 probe 只有传入以下全部参数时才使用正式 release；缺任一项即拒绝，而不是退回临时 release：`--r1-namespace-release`、`--r1-namespace-trust`、`--r1-namespace-state`、`--r1-runtime-release-hash`。state 首次创建还必须带 `--r1-bootstrap-approval-id` 与 `--r1-bootstrap-approver-id`。F2 在 SDK 导入前校验并激活 release，随后在控制面预留一个 own range ID；这一高水位动作不位于 C0--C7。

R2 的正常执行顺序是固定的：先用 `r1_r2_crash_boundary.py` 触发真实边界；再在**新的** runtime root 调用 F2 的 `--r1-recovery-route-ledger <crashed-route-ledger>`，它只执行两次全订单权威扫描并写入完整 `RECOVERY_REHYDRATED` batch，完成状态最多为 `RECOVERED_DISARMED`；最后才可在独立 runtime root 以 `--recovery-route-ledger <same-ledger>` 和明确的 `--recovery-approval-id`、`--recovery-approver-id` 执行唯一 own target 的限速清理。缺 batch、摘要不一致、多个 target、callback gap 或没有人工审批时均拒绝 cleanup。查询终态与精确 replay 子证据虽已闭合，该窄链路仍只是单系统 R2/P3 evidence，不能标记完整 R1 通过。

release 在首次 R2 前必须将 own range 之外的当前 scope 以已签名、不重叠的 `FOREIGN_RESERVED` lease 完整覆盖；不能把历史行静默当成 foreign。epoch 轮换还必须将旧 high-watermark 前缀从 successor own range 退出，否则 query 行没有 epoch 字段、恢复无法区分历史 own 与当前 own，必须在 SDK/session 前 fail-closed。若旧 release 已在真实 R2 前遗漏该覆盖，普通 rehydrate 必须以 `UNKNOWN_NAMESPACE → RECOVERY_BLOCKED` 退出。仅为消除该历史演练遗留的单一模拟盘委托，F2 提供独立的 `--r1-manual-cleanup-route-ledger`：它要求当前代码所绑定的 active release、另一个已签名的 historical source release/trust、崩溃 route 的 exact own PreDispatch、两次完整扫描中同一唯一 native identity、零 callback gap 和显式人工 approval，才允许限速撤销这一笔。historical release 只用于验证 route 的原始 directory hash，不能启动 session、分配 ID 或下新单；active release 只用于启动当前受控 session。该路径不写 `RECOVERY_REHYDRATED`、不投影任何 unrelated row、不把 namespace 标为健康，也不能替代正常 R2 rehydrate/A3/A6。

### 3.2 Linux 运行时隔离

| 对象 | A | B | 禁止共享 |
| --- | --- | --- | --- |
| 进程、EMT session、native caller | 独立 | 独立 | 同一 `TraderApi` 或同一 native caller |
| namespace release/state/fence | 独立 | 独立 | release-state、fence、route ledger |
| Journal generation/runtime root | 独立 | 独立 | mmap writer、callback writer |
| CPU 与日志目录 | 可隔离绑定 | 可隔离绑定 | 原始账户/订单 payload 写入 evidence |

所有 scope 保持 `DISARMED`。`A2` 与 `A3` 的受控委托必须复用既有有效、被动且可撤销的模拟盘 order plan；演练结束后至少等待柜台窗口并按限速清理。清理目标只能来自完整提交的 own `RouteLedgerV2`，不能由 CLI 直接输入 EMT order ID。上述历史遗留人工清理仍只从同一 route ledger 的 pre-dispatch fact 加双扫描推导目标，CLI 也不得输入 EMT order ID。

## 4. R1-A1--A6 执行顺序与证据

| 阶段 | 允许副作用 | 前置条件 | 通过摘要 | 失败结果 |
| --- | --- | --- | --- | --- |
| A1 | 无 | release/trust/approval、Git revision、SDK hash、Linux 工具均已就绪 | 签名、有效期、scope、范围、epoch/high-watermark 与负例均通过 | 不启动 SDK/session |
| A2 | 受控模拟盘委托/查询/清理 | A 与 B 有不同 release、scope、runtime root | A/B 分类正确；双方 foreign 均为只读摘要 | `DISARMED`，停止新单 |
| A3 | A 的一笔受控委托后强杀；B 持续 | A2、完整查询证书与明确 R2 断点驱动 | A 仅凭权威证据 rehydrate own；B 不受影响 | `RECOVERY_BLOCKED`，不重报/不撤单 |
| A4 | 无 | A1 | 伪造、过期、撤销、重叠、unknown、重复 native ID 全部 fail-closed | 零 SDK 副作用 |

每个 evidence 包至少记录：测试 revision、release/trust/SDK/profile 哈希、逻辑 scope 哈希、阶段、时间窗口、查询 completion 摘要、双扫描 digest、分类计数、callback gap、final gate 和清理结论。不得记录任何账户、证券、价格、外部订单 ID、地址、口令或私钥。

## 5. 已闭合证据、执行结果与剩余边界

1. **查询完成证书已闭合。** 三 scope 的完整 query-family 矩阵均以 EMT native `last/is_last` 作为唯一完成条件；不会以静默、行数或超时补写“完成”。最新 query-only 全量分页订单扫描无 submit/cancel/recovery 写入，且 callback gap 与静态 row-failure 摘要均为零。若 EMT SDK 或柜台行为变化，必须重跑矩阵；任何终态缺失立即 fail-closed。
2. **`RESTART` replay 已取得精确关联见证。** 每个 scope 都在独立、payload-free probe 中观察到两条与已签署受控身份对关联的 callback；`replay_correlated=true`。登录成功或泛公共流 callback 均不算证据，也不得外推为任意历史订单的全面 replay 承诺。
3. **R2 真实断点与窄恢复已通过。** 2026-09-11 已在 Linux EMT 模拟盘完成单系统窄链路：公开 release 在 SDK 前激活，`InsertOrder()` 同步返回后 marker 已 fsync，隔离 worker 在本地 `NATIVE_ACCEPTED` 落盘前被 `SIGKILL`，route ledger 仅有 PreDispatch/CallStarted、无 native receipt；两次权威订单扫描 digest 一致后，唯一 own route 被持久化为 `RECOVERY_REHYDRATED` 并保持 `RECOVERED_DISARMED`，随后以显式人工批准限速清理，独立只读 preflight 复核未完成订单为零、callback gap 为零。早期 release 的 historical 覆盖/范围复用缺口均按设计 fail-closed，遗留委托只经单目标手工清理移除。
4. **A1 静态门禁已通过。** 在 `75fa900` 上完成 `git diff --check`、Ruff、格式校验、Pyright 及 R1 定向回归集；本机和 Linux Git checkout 的同一 49 个 R1/ingress/mutation 用例均通过。Linux 演练目录不含源码上传，运行前后均保持相同 revision。
5. **A2、A3、A6 多系统与 R2 证据已通过。** A/B 使用独立 public release、state、runtime root、EMT session 与 native caller；双方双扫描、namespace route fence、callback gap-free 与 own cleanup 后未完成归零均为真。A3 在 `InsertOrder()` 同步返回后、本地 `NATIVE_ACCEPTED` 事实持久化前强杀 A，B 在 A 恢复期间保持；A 只重建 own route，并以显式人工批准、限速路径清理唯一 own target。最终只读 `QueryUnfinishedOrders` 核验为完整、未完成数为零、取消尝试为零。
6. **A4、A5 负例与故障矩阵已通过。** 签名、范围、unknown namespace、重复 identity、分页末页、查询不稳定、callback gap、mmap 尾帧与 host-health 的故障输入均保持 fail-closed；query-only、integrity-fault 和 capacity-fault 三类实际 Linux 核验均不产生委托、撤单、资金或信用副作用。
7. **性能回归已完成。** 同一冻结代码 revision 已完成 100 样本热态单笔、三轮 499 burst、OMS `2,000 TPS + 5,000 QPS` 与 EMT 499-burst 并行的 W7，以及每个实际下单窗口后的 cleanup。详细口径、分位数和限制见 [R1 统一验收与性能复验报告](../04-测试验收与性能/04-OMS性能与容量/06-R1统一验收与性能复验报告-2026-09-11.md)。
8. **仍不解除 DISARMED。** `full_r1_acceptance=false` 不是将失败改写为通过：证书中保留 `CALLBACK_REPLAY_INCOMPLETE`，因为已验证的是三 scope 的有限、精确关联 `RESTART` 见证，而非 EMT 对任意历史对象的可验证全面回放语义。故本轮只完成“同账户多系统下，本系统订单的 manual-only 权威识别、重建与精确清理”的受控演练；不允许自动恢复、自动撤单、自动重报或 `READY`。

## 6. 当前完成定义

本手册所定义的八项执行顺序已经在 `75fa900` 的 Linux EMT 模拟盘完成：冻结与 A1、A2、A3、A4/A5、A6、Hot100/499/W7 和证据收口均已留存脱敏 evidence。其完成定义是“同账户多系统下的本系统订单识别与 manual-only 权威恢复演练已完成”。

这**不**改变当前 `DISARMED`，更不等同 `READY` 或通用自动恢复证明。后续只有 EMT 提供可验证的全面查询/回放完成语义、并在新的冻结 revision 重跑相应证据，才可重新评估 `full_r1_acceptance`；不得用本地推测替代。
