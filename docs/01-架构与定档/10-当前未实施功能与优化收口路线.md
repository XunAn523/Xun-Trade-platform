## 3. P0：R1-P namespace 发布与完整权威恢复闭环

### 3.1 必须补齐的实现

#### R1-P1：生产 namespace manifest 生命周期

当前已有 canonical lease、签名验证、范围重叠检查、本地 namespace fence 和范围约束 allocator；真实探针使用的是受控临时 directory。需要将其收口为不含私钥的运行时发布物：

1. 定义版本化 namespace release 文件：own/foreign lease、账户范围摘要、交易日、`emt_client_id`、连续 token range、owner、adapter instance、release hash、签名、证书/公钥引用、有效期和撤销引用。
2. 实现只读 loader：在 SDK 导入、session 创建和新单准入前验证签名、发布者、有效期、撤销状态、scope 一致性及范围不重叠。
3. 将 active manifest hash、信任锚 hash 和 lease 高水位绑定到 release state；日切、轮换、范围耗尽、回滚或歧义均 fail-closed。
4. 私钥只能位于受限测试/发布控制面，不能进入 Git、evidence、Journal 明文或 C0--C7。

#### R1-P2：完整 EMT 权威恢复证书

当前 recovery collector 只接收完整 `orders` 查询的五个归一化标量；必须扩展为受 manifest 约束的完整证据包：

1. 接入分页订单、未完成订单、分页成交、资产、持仓及适用信用查询，逐类验证 request/cursor/末页/空结果/错误/超时语义。
2. 接入经验证的 `RESTART` callback replay，并将 recovery 期间 ingress 的 callback gap 覆盖纳入同一证书。
3. 若 EMT 缺少可验证 as-of，按“订单 A 扫描 → 未完成/成交/风险查询 → 订单 B 扫描”执行稳定双扫描；本系统和 unknown namespace 必须逐 `(order_client_id, order_emt_id, status, filled, leaves)` 稳定。
4. `FOREIGN_RESERVED` 仅记录脱敏摘要、数量及 drift，绝不投影、撤单或影响本系统 callback gap；unknown、冲突、分页不完整、负确认缺失、callback gap 均为 `RECOVERY_BLOCKED`。

#### R1-P3：可回放的 R2 rehydrate 事实

R2 恢复不能只修改内存中的 route 映射。必须：

1. 为每一个成功补建的 `(execution_id, order_client_id, order_emt_id)` 追加独立 `RECOVERY_REHYDRATED` 事实，包含原始 PreDispatch/`CALL_STARTED` 引用、权威查询摘要 hash、manifest hash 和 recovery run ID。
2. 由 Journal-first projector 幂等投影该事实，重建双向 native ID 映射；不得改写旧 frame、伪造 `NATIVE_ACCEPTED` 或改变历史 position。
3. 任何 blocking reason 先阻止所有 rehydrate 写入；所有映射、OMS state、evidence 和 gate 必须保持原样或完整新状态，不能出现半提交。
4. 恢复最终状态最多是 `RECOVERED_DISARMED`；人工审批、最新风险快照和其他账户 gate 仍是未来 `READY` 的独立前提。

#### R1-P4：同账户多系统运行组合

以两个独立 TradeCore 进程/发布目录模拟系统 A、B：不同已签名 namespace，优先不同 `emt_client_id` scope；各自拥有独立 fence、route ledger、Journal generation、session 与 native caller。不得把本机 `flock` 表述为跨系统全局锁，也不得在同一 EMT session 内并发调用 SDK。

### 3.1.1 2026-09-11 实施/探针补记

本轮不改变恢复的 fail-closed 结论，只补齐了两个安全边界。

1. F2 在 native `InsertOrder()` 已受理、而后续权威查询失败时，必须在 session 停止前走同一条 `guard → prepared route → scheduler → EMT CancelOrder()` 的**唯一精确目标**清理。清理不按账户扫描撤单，不重试 CancelOrder；随后只读轮询 `QueryUnfinishedOrders`，直到权威归零或有界超时。
2. 如果原 F2 进程已经退出，恢复清理只能从其完整提交的 mmap `RouteLedgerV2` 读取一个 `PreDispatch + NATIVE_ACCEPTED` 匹配对。帧撕裂、非零尾部、多个 target、缺失或冲突映射一律拒绝；不会接受 CLI 输入的任意 EMT ID 作为取消目标。
3. 随后的新鲜完整 certificate 尝试如期因 `onQueryOrder` 缺少末响应而失败；异常路径没有将其误报为恢复成功。其唯一已受理目标由独立 F2 进程从该次提交的唯一 `PreDispatch + NATIVE_ACCEPTED` 路由账本恢复，显式使用 `fengyu` 的单目标清理 approval，经 guard/route/scheduler 限速撤单后取得 terminal、`QueryUnfinishedOrders=0` 与 zero callback-gap。该清理只证明“本次已知 target 已清除”，不构成完整查询证书或通用 R1 恢复成功。
4. 同一发布物随后完成 Linux 离线 preflight：public release/trust 的签名、scope、runtime revision、有效期和 R1 工具链均通过；该步骤不导入 SDK、不读账户文件、不用网络、不写 release state，也不产生券商副作用。
5. Linux 离线 R1-A4 负例预检已重新执行：scope/runtime hash 不匹配、过期 release、伪造签名、已撤销 signer 均被拒绝，且确认无 SDK 导入、无账户文件、无网络、无 release-state 写入及无券商副作用。范围重叠和 route/native ID 冲突仍由 R1 定向回归测试覆盖；它们不能取代后续 A/B 实际窗口。
6. M3 已支持按当前 host 的严格 SDK 文件集运行。早期 15 秒公共流观察不足以构成回放证明，现已由每个 scope 的 signed, payload-free exact witness probe 取代：普通、信用、期权均有两条与受控身份对精确关联的 callback，且 `replay_correlated=true`。无关公共 callback 不被计数；该证据只覆盖所见身份对，不声称 EMT 对任意历史对象提供全面 replay。
7. M3/Linux 支持代码更新后，服务器源码 revision 已变化；即使变更没有触及订单执行逻辑，R1 的 runtime release hash 仍会使旧签名 release 拒绝新 checkout。下一次 R1 有副作用演练前必须在受限发布控制面为该精确 revision 签出新的 release，不能复用本轮 epoch 3 release 或绕过 hash gate。

真实模拟盘已验证该定向清理可完成“原生撤单受理 → terminal → 未完成订单归零 → zero callback gap”。此前的 R1 查询失败样本本身仍是失败 evidence，不能因此转为 R1 通过。

SDK 随附 Python 示例要求 `onQueryPosition(..., last, ...)` 在一个请求的最后响应中给出 `last=true`。历史 probe 曾缺少该终态并已作为失败 evidence 保留；最新三 scope query-family 矩阵已按该语义完成。TradeCore 仍不会以“行数少于预期”“短暂静默”或定时器代替末页/末响应证明；未来 SDK/柜台版本变更必须重跑该矩阵，任何终态缺失立即恢复为 `RECOVERY_BLOCKED`。

为使 W7 的 query-only 清理门禁不被 vendor Python binding 的析构停滞误判，
`gateway-mutation-recovery` 增加了仅供一发性只读证明使用的
`--mutation-recovery-isolate-after-report`。它只在完整报告与脱敏 trace 落盘后直接退出，
不会改变查询、委托、撤单或恢复 gate。2026-09-11 已实际验证该模式正常退出并得到未完成数为零的
fresh proof；它不消除有限 callback witness 不能外推为通用 replay 的边界，也不改变 `DISARMED`。

验收证据至少包含 release/SDK/profile/manifest hash、查询窗口与完成摘要、双扫描 digest、分类计数、foreign 摘要、callback gap、最终 gate、清理结论和测试 revision；不得包含账户、标的、价格、订单号、地址、密码或私钥。

### 3.3 R1 后的回归要求

R1 修改 namespace、route ledger、query ingress 或 callback 分类后，必须在同一代码 revision 重跑受影响的 F1/F2/F4/F6 检查：100 样本热态单笔、三 scope 499 burst、完整 C0--C7 时间对、callback gap、清理闭环，以及 OMS W7 并行非干扰。旧 revision 的性能 evidence 不得移植为新 release 结论。

## 5. P2：明确延期的产品扩展

### 5.1 F5：真实 PaperBroker 与 QMT

PaperBroker 必须先获得已授权外部 release、artifact hash、许可证、schema、运行时身份和隔离实例，随后实现 submit/cancel/query/recovery、RouteToken 回显、事件归一化、断连/重连和故障隔离。现有 fixture 不可替代真实接入。

QMT 若要对外声明可用，必须取得 SDK、账户、scope ownership、mapping/capability manifest、订单/成交/撤单错误/分页查询/回放的回显证明，以及与 EMT 同等级的恢复与性能验收。已定档的 Linux/Windows Edge 边界、`QmtBrokerAdapter` 责任和 P0--P4 顺序见[QMT Windows 边缘适配定档](./16-QMT-Windows边缘适配定档.md)。当前 fake profile 必须继续拒绝真实 submit/cancel。

### 5.2 EMT SDK 全接口能力矩阵

当前 EMT-only 执行闭环不等同于官方全部 API/SPI 覆盖。若产品目标扩展为“SDK 全覆盖”，需对每个 API/回调分别完成 capability、合法 fixture、空/非空/分页/超时/断线语义、性能样本和发布门禁。供应包缺失或账户不支持的接口必须显式标为 `unsupported`，不得以 fake 成功填补。

## 6. P3：不属于当前承诺的高可用扩展

当前 mmap Journal 只处理“TradeCore 进程崩溃、操作系统仍运行”的本机恢复边界，不承诺主机掉电、操作系统重启、磁盘损坏或跨主机自动接管。若未来需要这些能力，必须新建独立故障域设计：远端不可篡改审计锚、独立复制/仲裁、跨主机 ownership、RPO/RTO 和灾难恢复演练；不得把异步 SSD archive、PostgreSQL 或当前 mmap 脏页误表述为自动高可用。
