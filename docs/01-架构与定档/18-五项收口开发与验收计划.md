### 1.1 全程不变量

1. 策略数据面只能携带策略身份、binding、订单/查询意图和脱敏结果；绝不能传递、回显或持久化柜台账号、密码、交易地址、JWE 明文或私钥。
2. 凭据只能通过配置控制面由受控身份提交，并在 Linux 侧的 `SecretProvider` 中以引用形式保管。执行热路径只取得已经激活的 adapter runtime，不读取控制面数据库、不解密 JWE、不进行 TLS 握手。
3. 每一笔带副作用的执行都必须使用不可复用的 execution identity、binding generation/epoch、journal 事实和准确的 owner 路由；不允许通过“重试一次看看”补偿不确定状态。
4. `PollEvents(cursor)` 是 Consumer 事件恢复的权威接口。UDS push 只是低延时通知和游标提示，断线、溢出、重连后必须从权威 cursor 补读。
5. 任一 adapter、scope、tenant、账户或 namespace 的错误不得泄漏给其他 binding；账户共享时，路由仍必须以 client identifier / ownership namespace 区分本系统订单与外部系统订单。
6. 任何未知 callback、查询终态不完整、凭据版本不一致、恢复对账不完整、队列超限或外部 SDK 能力缺失，均为 fail-closed 证据，不得伪造成功或静默降级。
7. `READY` 仍受 EMT 权威查询/回放语义与真实故障演练证据约束。本计划中的实现或离线测试最多证明某个子能力可部署、可观察或 `RECOVERED_DISARMED`。

## 4. W1 / S1：Consumer V2 → EMS → EMT-only Adapter Runtime 组合

### 4.1 目标与边界

将已存在的 Consumer 协议、OMS 事实、EMS 路由和已激活 adapter binding 组合成一个可替换、可停止、可恢复、按 binding 隔离的 EMT-only 执行运行时。目标是让上游策略只提交业务意图，并让执行事实通过统一 cursor/event 路径返回；不是让 Consumer 直接持有 `TraderApi` 或凭据。

首轮只接通 EMT adapter。QMT、PaperBroker 和其他 adapter 仅以相同抽象被注册，不能因占位实现被解析为可执行目标。

### 4.2 计划代码修改

| 模块/文件（计划） | 修改内容 | 热路径约束 |
| --- | --- | --- |
| `xuanling_tradecore/consumer/runtime_composition_v1.py` | 定义 `ConsumerExecutionRuntimeV1`；启动/停止顺序、依赖注入、health、generation fence | 启动期解析依赖；不在每单查询控制面 |
| `xuanling_tradecore/consumer/execution_dispatch_v1.py` | 将已提交 operation 转为 EMS command，按 `binding_id + generation` 稳定分发 | 只读取不可变 binding snapshot；单次执行不加全局锁 |
| `xuanling_tradecore/ems/adapter_runtime_registry.py` | `AdapterRuntimeRegistry`、原子 activate/drain/revoke、引用计数与 generation 比较 | 查表 O(1)；旧 runtime 只 drain，不接受新单 |
| `xuanling_tradecore/oms/execution_fact_reader.py` | 读取 Journal/OMS 已提交事实、幂等 key 与恢复 watermarks | 事实优先；重复读取不得重复下单 |
| `xuanling_tradecore/adapters/emt/runtime_factory.py` | 从已验证 profile/reference 建立 EMT runtime；向 EMS 暴露 submit/cancel/query 接口 | 只接收已解析的无密配置；原生 SDK lane 规则保持不变 |
| `xuanling_tradecore/consumer/operation_service.py` | operation 状态从 `accepted`、`dispatched`、`adapter_acknowledged` 到 terminal 的统一投影 | 不把 SDK 同步返回误写为柜台最终成功 |
| `tests/consumer/`、`tests/ems/`、`tests/adapters/emt/` | fake 与受控 native-adapter 集成测试 | 外部副作用测试必须 opt-in、DISARMED 默认 |

若仓库实际模块名不同，实施时可调整文件名，但必须保留上述职责边界和对应测试。不得将这些职责塞入 HTTP 路由、策略 UDS handler 或控制面 handler。

### 4.3 分阶段实施

#### S1.1：运行时注册表与 generation 栅栏

实现不可变 `BindingRuntimeSnapshot`，字段至少含 binding、adapter 类型、scope、generation、状态、capability digest 与 runtime handle。`activate` 只在批准 revision、secret 引用可解析、adapter preflight 成功后原子发布；`revoke` 先拒绝新单，再 drain 在途命令，最后关闭资源。旧 generation 到达的执行必须返回 `BINDING_GENERATION_STALE`，不得重定向到新 runtime。

验收：

1. 100 次 activate/revoke/rotate 并发交错中，任意 execution 只命中一个 generation。
2. revoke 后新 execution 被拒绝；已进入 runtime 的 execution 有可审计 terminal 或明确 `UNKNOWN_REQUIRES_RECONCILIATION`。
3. 两个 binding 指向同一 adapter 类型时，route、事件和 health 不可串扰。
4. registry 读取路径不访问 PostgreSQL、SecretProvider 或网络；用测试 hook 证明。

#### S1.2：OMS 事实到 EMS command 的幂等分发

以已提交的 operation/execution fact 为唯一输入。分发器必须先写入或确认 dispatch intent，再调用 adapter；同一 `(binding_id, execution_id, action)` 的重复投递只返回已有结果或继续恢复，不得产生第二次 `InsertOrder`/`CancelOrder`。订单、撤单、只读查询分三类 command；撤单必须验证原 order 的 binding ownership。

验收：

1. 同一 execution 被重复调用 10 次，fake adapter 的 side-effect 计数严格为 1。
2. 在“intent 已持久化、adapter 尚未调用”“adapter 同步返回、投影未完成”“callback 到达、重复消费”三个注入点中断，重启后无重复副作用。
3. 取消其他 binding 的订单明确 `ORDER_OWNERSHIP_DENIED`，不调用 adapter。
4. 只读 query 可并行，但不得绕过 binding/capability gate。

#### S1.3：EMT-only runtime 适配与 callback 归并

将 EMT 的 submit/cancel/query adapter 接到 registry；保留既有 SDK native lane、pre-dispatch marker、client identifier/ownership namespace、callback ingress、Journal 和 projector。Consumer 不直接解释原生 callback，而是由 adapter 先形成统一 execution event，再由 Consumer 通过 cursor 读取。未知 client identifier、未密封路由、终态不完整或 SDK 缺 capability 均必须输出结构化失败。

验收：

1. 受控 fake native adapter 走通 `operation → dispatch → adapter acknowledgement → callback → Consumer event`，每一事件携带同一 execution/binding/generation。
2. EMT contract fixture 覆盖同步返回、异步受理、异步拒绝、重复 callback、未知 callback、取消和 query 的 normal/fail-closed 路径。
3. Linux SDK 探针只在显式 profile 下执行；缺失 binding 时记录 `CAPABILITY_UNAVAILABLE`，不以 Python mock 冒充原生通过。
4. 外部模拟盘或真实最小副作用验收只在批准 profile 下进行，并在测试末尾执行查询/撤单清理核对；没有完整 callback/查询证据即失败。

#### S1.4：停止、恢复与发布接口

实现 runtime 的 quiesce、drain、stop、restart、readiness reason 和 evidence export。停止顺序为：拒绝新 Consumer operation → 等待 EMS 有界 drain → 固化 cursor/watermark → 关闭 adapter runtime。恢复顺序为：载入已批准 generation → 建立 adapter（仍 DISARMED）→ 恢复事实/projector → 执行外部权威对账 gate → 允许受控 operation。没有 EMT 可验证回放/完整查询终态时，恢复状态只能是 `RECOVERED_DISARMED`。

验收：

1. 在 dispatch、callback、projector、drain 四个点终止进程；每次重启均产生确定状态，不出现“成功但没有外部/事实证据”。
2. restart 后旧 generation 的请求被拒绝；新的 approved generation 可查询 health，但不因重启自动放开交易。
3. restore evidence 缺失、callback query 不完整、ownership 不明时，readiness evaluator 给出可机器读取的阻塞原因。
4. 完成该包后，将状态标为 `CODE_COMPLETE_PENDING_ACCEPTANCE`；只有 S1 集中验收完成才改为 `ACCEPTED`。

### 4.4 W1 集中验收与完成定义

集中验收环境必须使用 Linux CPython 3.10、匹配的 EMT SDK、隔离 profile、明确的 scope 与无密 evidence export。顺序为：离线回归 → 受控 runtime 启停 → 只读 capability → 模拟盘最小 submit/cancel（如已批准）→ 故障矩阵 → 清理/证据归档。

通过条件：所有测试均能提供 execution/binding/generation/cursor 的闭环；无重复 side-effect；无跨 binding；无密泄漏；故障不误报成功；清理核对无遗留本系统订单。该结果证明 EMT-only runtime 组合可验收，**不**证明 EMT 的三项查询终态问题、完整回放权威性或总系统 `READY` 已解决。

## 5. W4 / S2：Consumer 事件投递、快照、watermark 与 health

W4 依赖 W1 的统一 execution 事实源，但其实现不得向 C0–C7 的原生下单热路径追加 Redis、数据库、同步 UDS 写入或等待 consumer。热路径最多写既有 Journal/事实；投递与投影在旁路 worker 完成。

### 5.1 计划代码修改

| 模块/文件（计划） | 修改内容 | 关键约束 |
| --- | --- | --- |
| `xuanling_tradecore/consumer/event_log.py` | 事件序号、binding 分区、cursor 编解码、dedupe/retention 元数据 | cursor 单调、不可猜测、跨 binding 无效 |
| `xuanling_tradecore/consumer/event_stream_server.py` | Unix-domain socket server-push framing、subscribe/ack/resume、每连接有界队列 | 不阻塞 producer；慢客户端被明确 backpressure/disconnect |
| `xuanling_tradecore/consumer/snapshot_projector.py` | 从 OMS/EMS/adapter event 生成订单、执行、health、capability snapshot | snapshot 含 source cursor/watermark/stale 状态 |

### 5.2 分阶段实施与验收

#### S2.1：权威 event log 与 cursor 语义

定义 event 的不可变 envelope 和 cursor 范围。cursor 至少绑定 tenant、strategy/binding 授权范围、事件分区与 generation；错误 scope 的 cursor 必须拒绝。重复读可以返回相同事件，不能跳过事件；超出 retention 或出现 gap 时返回明确错误和最早可用 watermark。

验收：100 万条纯内存 fixture 的 cursor 单调性；跨 binding cursor 复用拒绝；重复/乱序/损坏 cursor 分别可定位；恢复从最后确认 cursor 继续且不漏事件。

#### S2.2：快照 projector、watermark 和 stale 语义

实现按 binding 分区的 projector。快照必须列出 `as_of_cursor`、`source_watermark`、`projector_lag`、`stale`、`reconciliation_required` 和 capability/readiness 原因。projector 暂停或事实源不完整时，快照必须标为 stale，而不是返回过期数据却标记正常。

验收：暂停/恢复 projector；注入 event gap；重建 snapshot；对比 event replay 与 snapshot，订单/状态/计数一致。故意删除一条事件时，projector 拒绝把后续状态标为 authoritative。

#### S2.3：UDS push 与背压隔离

实现本机 UDS 的握手、授权范围、订阅、ack、心跳、断开重连协议。每个订阅者使用独立有界 ring/buffer，达到上限后发送一次 `BACKPRESSURE` 控制帧并断开或降级为 cursor 提示；绝不让一个慢策略阻塞其他策略、projector 或 native callback worker。

验收：一个慢 subscriber、一个正常 subscriber、一个恶意不 ack subscriber 并行运行；正常 subscriber 连续收到完整事件，慢 subscriber 得到可恢复 cursor；producer 侧延迟和队列深度不随慢客户端无界增长。

#### S2.4：恢复、审计与接口兼容

断线客户端以最后 ack cursor 调用 `PollEvents` 完成补读，再恢复 push。所有 push event 必须可用 PollEvents 找回；PollEvents 则允许无 push 连接独立使用。保留旧 Consumer V2 接口兼容性，新增字段只为 optional。

验收：断线/重连/服务重启/retention 超限/跨 generation 场景分别有可重复测试；协议兼容测试通过；审计日志只输出 hash/cursor，不含敏感配置。

### 5.3 W4 集中验收与完成定义

集中验收执行 W6 类故障演练：replay、projector pause、snapshot stale、subscriber burst、slow consumer、service restart。证明的是“旁路事件系统可恢复且不阻塞热路径”，而非柜台事件一定完整。W4 通过要求每个 push 事件能回查权威 cursor，所有 stale/缺口均 fail-closed，且性能回归在 W3 中未检测到超出基线的热路径影响。

### 6.2 分阶段实施与验收

#### S3.1：数据库仓储与 migration

把 in-memory registry 的语义逐项迁移到 PostgreSQL：revision 单调性、审批的双人/角色约束、idempotency key、binding generation、revoke、审计 append-only、并发 conflict 和外键约束。迁移必须可重复执行，应用账户不得拥有 DDL/超级用户权限。

验收：空库升级、重复升级、并发同 revision、批准/撤销竞争、事务中断、重启后查询；所有不变量与 in-memory contract fixture 一致；审计行不可由运行时应用更新或删除。

#### S3.2：生产 SecretProvider 与密钥生命周期

实现受控后端适配器（实际产品由部署配置决定），统一返回 opaque reference/lease，不把凭据写入 PostgreSQL、配置文件、Journal、证据包或错误栈。rotation 创建新 revision 和新 reference；revoke 使旧 reference 不可用于新 runtime，同时由 W1 registry 完成 drain。

验收：模拟 secret backend 的过期、拒绝、轮换、撤销、重复请求、网络失败；失败时没有半激活 binding；异常/日志/审计的敏感扫描为零。实际 provider 的联调只在受控主机完成，证据只保留 provider 类型、reference hash 和结果码。

#### S3.3：mTLS/HTTP2 服务工厂与部署隔离

建立控制面专用 CA/trust store、服务证书、client principal allow-list、TLS 1.3/HTTP2 配置、请求大小/频率限制和 health endpoint。服务只监听规定网络范围；QMT envelope 转发保持 opaque。普通策略 UDS/TCP 数据面端口不得复用控制面 listener。

验收：有效 principal 成功、未知 CA/过期证书/错误 SAN/错误 principal/非 HTTP2/JWE 解密失败均拒绝；启停/reload 不丢审计；端口、ACL、进程用户、文件权限和网络规则符合部署规范。

#### S3.4：部署、回滚与与 runtime 激活联动

systemd service 使用专用无登录用户、限定写目录和最小 capability。部署执行 migration → 启动 control plane → probe → 创建 test profile/revision（仍 DISARMED）→ approval → binding activate → revoke/rollback。回滚只允许软件版本回退；已发布 revision 不能静默倒退，必须生成 successor 或明确 deny。

验收：在干净 Linux 测试节点从 Git 取代码、建 `.venv`、迁移、启动、重启、证书轮换、rollback deny 全过程通过；配置与日志无敏感信息；运行时可以读取已批准 binding snapshot，但不会在每笔订单访问控制面。

### 6.3 W2 集中验收与完成定义

集中验收以“受控配置角色可安全提交、审批、激活、轮换、撤销 adapter 配置；策略面完全不可读取/传递凭据”为目标。完成证据包括 PostgreSQL migration/重启、mTLS+JWE 负面矩阵、secret 生命周期、systemd ACL、runtime activation/revoke 联动和脱敏审计链。结果始终保持 `DISARMED`，并不授权外部交易。

| gates | 将 profile digest、代码 commit、环境指纹、baseline compare、清理核对和 `DISARMED` 状态写入 machine-readable result manifest |

### 8.2 分阶段实施与验收

#### S5.1：测量完整性和环境冻结

固定 Linux 主机、CPU governor/亲和性、内核、Python 3.10/.venv、SDK digest、配置 profile、adapter generation 和采集版本。对每次测量验证开始/结束/相邻分段的 timestamp 完整性；任何 C0–C7 或 Consumer/EMS 段缺口均为无效，不参与 P 值或平均值。

验收：连续三轮 dry-run 生成完全配对样本；环境指纹一致；时钟源单调；报告显式列出 drop/gap/invalid count。

#### S5.2：低并发热态单笔基线

对 100 条独立热态信号执行同口径测量，报告每条 C0–C7、两段项目内部总延时、Consumer/EMS 旁路时间、P50/P95/P99/P100 和完整批次 wall-clock。单笔基线与 burst 分开报告，不能把 499 排队结果用作单笔结论。

验收：100 条原始样本完整；预热与测量窗口明确；无隐式批处理、无复用近似样本；只统计项目内部时间，EMT callback/柜台时间单列。

#### S5.3：499 笔全接纳 burst

一次性连续释放 499 笔原始信号，采用已批准 order plan 与安全测试价格；记录 C0/C0A 到 C7 的逐笔时间戳、499 整批 submit wall-clock、第一条/最后一条 callback 到 C7 wall-clock、accepted/throttled/rejected/callback gap 与清理状态。不得创建 499 个线程或分批平滑发送。

验收：499 的释放方式、有效订单、scope/generation、外部接受数量和 callback 覆盖可复核；若 EMT 限流、路由错误、回调缺口或清理失败，报告应判失败/受限，而非过滤样本。

#### S5.4：OMS、EMS 与策略消费容量

依次运行：OMS fact-ingest ≥ 2,000 TPS、snapshot query ≥ 5,000 QPS、EMS command acceptance/dispatch 指标、策略 Consumer PollEvents/push 消费指标，并运行 W0–W6 基础故障测试。W7 在上述旁路负载与真实 EMT 499-burst 并行时执行，证明旁路不会影响热路径；若外部测试未获批准，可运行 fake-adapter W7 并明确标注，不能声称 EMT 实测通过。

验收：每项输出 open-loop/closed-loop 模式、并发、payload、拒绝/背压率、HDR、CPU/内存/GC/网络、原始摘要和 SLA 判断；同时负载下 C0–C7 与单独基线比较使用事先定义的非劣化门槛。

#### S5.5：性能发布判定

性能接受只要求“测量有效且未违反已定义基线/容量门禁”。它不接受以某一次较快 P50 掩盖 P99/P100，或用外部柜台时间评价项目内部代码。若 W1–W4 任何功能验收失败，性能结果只能归档为诊断，不可作为发布通过。

### 8.3 W3 集中验收与完成定义

完成物为一份按统一标准生成的性能证据包：配置与环境摘要、所有 workload 原始脱敏样本、HDR、系统证据、图表、异常样本、结论和复现实验命令。必须分别写明：项目内部 C0–C4、C5–C7、Consumer/EMS/策略旁路、EMT 外部 callback/柜台等待，以及不能相加的累计指标。通过后只更新对应 revision 的性能基线，不承诺跨硬件、跨 SDK、跨柜台环境一致。
