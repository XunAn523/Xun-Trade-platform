# EMT 模拟盘接口实测报告（2026-08-25）

> 历史归档：本报告记录 Windows 环境的既有实测事实。当前项目仅支持 Linux x86_64；本报告不能作为 Linux 支持、性能验收、发布或生产判断依据。

## 结论

已在 Windows CPython 3.10.11、EMT Python SDK `2.27.0.0` 上，对普通、信用、期权三个模拟资金账户完成供应商样例的全接口扫描。每个账户均有 85 个 Python binding 方法实际返回；映射到官方 2.27.0 矩阵后，`TraderApi` 为 **83/86 实际调用**，`TraderSpi` 为 **53/69 实际观察到**。

这不是“86/69 全部成功”的结论：当前 Python binding 缺少两个信用划拨接口及其回调，另外 14 个可绑定回调在本轮模拟盘业务条件下没有发生。所有缺口均保留为缺口，不能作为生产验收通过依据。

## 环境与方法

- 平台：Windows x86_64；解释器：CPython 3.10.11；SDK：`vnemttrader` 2.27.0.0。
- 账户：普通、信用、期权三个模拟盘账户；账户、地址、密码位于被 Git 忽略的 `data/performance/config/emt/`，未进入本报告或版本库。
- 执行器：`vendor-simulated-sweep`。它在内存中运行 SDK 自带 `test/tradertest.py`，保留其交易、撤单、资金、信用、期权调用顺序和示例参数；补足供应商样例遗漏的已绑定接口。
- 安全：SDK 的控制台输出在登录与扫描期间被丢弃；报告不保存业务回包、账户或密码。
- 指标含义：供应商扫描的 `return` 延迟是 Python 调用进入原生 SDK 到返回的同步耗时，并非柜台最终处理时延。C0→C5 仅以独立的低频只读基线为准。

## 网关 C0–C7 低频只读复测

同日在 Windows CPython 3.10.11、EMT Python SDK `2.27.0.0` 上，以网关的 `gateway-readonly-c0-c7` 驱动对普通模拟盘执行一轮串行复测。驱动实际经过 cross-platform loader、`EmtSession`、facade、SPI bridge、原生 fastspi、事件 Journal 与 ACK，不保存账号、标的或 callback payload。

`QueryAsset`、`QueryFund`、`QueryPosition`、`QueryUnfinishedOrders`、`QueryOrders`、`QueryTrades`、`QueryIPOQuotaInfo`、`QueryIssueInfoList` 均得到 `ok`，每条链路具备 C0–C7。每项仅一条样本，故报告状态仍为 `insufficient_samples`，不能作为 P0 或生产 SLA 验收。`QueryIPOInfoList`、`QueryYesterdayAsset` 的终结 callback 缺失在本轮再次复现；它们被保留在 86 接口矩阵和单独诊断探针中，但不再混入“完整 C0–C7”只读基线。

信用模拟盘的共同 6 项查询均得到 `ok`。期权模拟盘中，`QueryAsset`、`QueryPosition`、`QueryUnfinishedOrders`、`QueryOrders`、`QueryTrades` 均得到 `ok`；`QueryFund` 完成本地调用（C0–C4）但没有 C5–C7。首轮与随后 3 轮复测均为超时（共连续 4 次），因此将其列为**仅期权档案**的已知终结 callback 缺口。该项保留在矩阵和显式探针，不得作为成功 C0–C7 样本，也不得据此声明期权资金查询已满足性能标准。

## 受控下单/撤单链路首次执行

在普通模拟盘上以 `gateway-mutation` 执行一次受控周期。该驱动限制为一次普通限价委托、一次 `QueryOrderByEMTID` 回查、一次仅针对本次返回订单 ID 的撤单，以及第二次回查；无自动重试，订单参数、账号、凭据、原生订单 ID 与业务回包均未写入报告或代码仓库。

本轮下单和撤单均已越过原生调用返回边界；下单的首个完整 C0–C7 与首次回查已完成。撤单阶段发现 EMT 会为同一命令关联的订单状态发送重复通知，而当时的 trace 实现会重复写入命令 C5，导致 `TraceError` 中断报告生成。因此本轮**不得作为** `InsertOrder`、`CancelOrder` 或 `OnOrderEvent` 的性能样本，也不得据此断言最终业务状态。

问题已修复：命令只使用首个匹配 callback 记录 C5–C7；每个重复原生通知仍各自保留完整 SPI trace。修复后核心测试为 48 项、性能测试为 40 项全通过，并以普通模拟盘的 8 项只读 C0–C7 查询复核会话与回调通道，结果均为 `ok`。

### 2026-08-26 10:30 callback 尾部复核与归档验证

第二个十周期报告再次出现 `OnOrderEvent` 约 0.9 秒的 C0→C7 p95。排查确认：首个订单 callback 已完成命令链路后，后续重复状态通知会在回查与限速等待期间停留在 command ring，直到下一次命令等待时才被 ACK；该延迟来自压测器未持续消费，而非 EMT callback 或 Journal 的服务时间。因此前两个十周期报告中的 `OnOrderEvent` C0→C7 尾部数据不纳入后续验收比较。
