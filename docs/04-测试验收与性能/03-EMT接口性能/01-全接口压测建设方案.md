# EMT 网关全接口压测建设方案

## 目标与现状

目标是确认**网关**的全接口性能瓶颈，而不仅是 EMT Python SDK 的调用返回时间。每一项证据必须能用同一 `correlation_id` 关联请求、SDK 调用、原生回调、网关持久化和策略 ACK。

2026-08-25 的 Windows 模拟盘结果仅为历史连通性与低频查询记录，详见[实测报告](./历史报告/2026-08-25-EMT模拟盘接口实测报告.md)。当前项目仅支持 Linux，因此该记录不能用于 Linux 或全接口性能验收：当时仅实际调用 83/86、实际观测 53/69，且全接口扫描没有 C0–C7 关联链路。

本阶段已建设以下 P1 基础设施：

- `tools/performance/perfbench/matrix.py`：从官方 86 个 `TraderApi` 和 69 个 `TraderSpi` 自动展开接口、账户档案、workload、必需时延路径和 P0/验收样本门槛。
- `tools/performance/perfbench/trace.py`：线程安全的 C0–C7 采集器；仅接收关联 ID、接口元数据、单调时间戳、结果与白名单资源指标，不接受业务 payload 或凭据。
- `tools/performance/perfbench/gateway_report.py`：严格汇总器。任一场景无记录、阶段缺失、样本不足或失败都会保留为非通过状态。

P2 的持久化与 binding 门禁已具备可测实现：`emt_gateway.journal.FileJournal` 使用二进制 `header | identity | CRC32C commit` 帧，在每次 append 后执行 `os.fsync`，启动时只保留连续校验通过的前缀并截断损坏尾部；记录中只保存命令 ID、关联 ID 和 SHA-256 摘要。`EncryptedReplayStore` 使用部署注入的 Fernet 密钥保存加密 payload，`CommandCustody` 在写入 `COMMAND_PREPARED` 前先完成该保存；跨进程 lease 防止两个网关拥有同一 journal。恢复时 `CALL_STARTED` 和 `SUBMIT_UNKNOWN` 只能进入人工/权威查询核对队列，禁止自动重发。`emt_gateway.capabilities.inspect_trader_api` 与 `EmtTraderFacade` 分别逐项检查并登记官方 86 个 `TraderApi`。当前工作区 SDK 静态检查结果为 **83 个 direct、`RegisterSpi` 由 69 个 SPI bridge adapter 覆盖、2 个 unsupported**：`CreditMarginAvlTransfer` 与 `QueryCreditMarginAvlTransfer`。这是一项 binding 能力证据，不是接口实测成功或性能验收结果。

## 压测矩阵

矩阵覆盖每一个 catalog 接口及其既有 workload，并按能力选择 `ordinary`、`credit`、`option` 三类模拟账户。普通订单、撤单、账户状态和对应回调在三个账户档案中分别执行；信用和期权专属接口保持在对应账户档案中隔离执行。

| 接口档位 | 必需链路 | P0 / 发布最小成功样本 | 运行方式 |
| --- | --- | --- | --- |
| `LIFE` | `C0→C1→C3→C4` | 10 / 30 | 单线程；冷启动、失败。 |
| `CMD-H` | `C0→C1→C2→C3→C4`，关联 `C0→C5→C6→C7` | 100 / 1,000 | 稳态、突发、流控、恢复。 |
| `CMD-A` | 同 `CMD-H` | 30 / 100 | 受控串行或已证明的 lane；每次副作用可审计。 |
| `QUERY` | `C0→C1→C3→C4`，首回调至 `C7` | 100 / 1,000 | 稳态、突发、空结果、分页、迟到回调。 |
| `CB-S`、`CB-H`、`CB-A`、`CB-Q` | `C0→C5→C6→C7` | 30/100、100/1,000、30/100、100/1,000 | 重连、乱序、重复、慢消费者、分页和错误。 |

样本数量是统计门槛，不是直接的柜台发射速率指令。每个场景的 fixture、执行窗口、并发阶梯、限流上限和负责人须写入本机 `runbook`；账号、密码、地址、标的和业务参数不得出现在 runbook、trace 或 Git 中。

稳态证据不能替代非稳态证据。`workload-plan-template` 从同一矩阵生成独立的本机控制清单，覆盖所有非 `steady` 场景，并固化每类工作负载的最低控制项：突发需已批准 lane、持续窗口和背压观测；空结果需空数据 fixture 与终结回调；分页需多页 fixture 与尾页核对；迟到/失败/恢复/重连及 callback 的重复、乱序、慢消费者、storm 必须有相应的受控注入和恢复、对账或队列核对。清单只接受 fixture ID、负责人和本地受控登记引用，不保存业务参数。外部 `gateway-fixture` 真正执行模拟盘前必须校验该清单与主 runbook 的 owner/fixture 一致，避免将当前 60 个稳态通过场景误报为全负载覆盖。

`gateway-workload-readiness` 会把非稳态的控制清单、主 runbook 对齐与真实 C0–C7 P0 证据作为三道独立门输出，并按 workload 汇总每类未填控制项和未通过证据。它既不因已有稳态 trace 放行，也不因填写了清单而伪造实测通过；该报告是排期、fixture 评审和后续外部执行的唯一缺口视图。

首个内置非稳态 runner 为 `gateway-query-burst`：对当前本机已启用的只读 `Query*` fixture，先以 2 个独立 request-id 做最长 2 秒的完整 callback 链路 capability probe；只有 probe 的两个请求都完成，才以每 lane 2--4 个独立 request-id 连续发起请求、再统一 drain callback。默认 25 轮 × 4 为每个已选查询接口提供 100 条真实 `burst` 候选样本；probe 失败时只归档真实阻断，不进入扩容。该 runner 不执行订单、撤单、资金、信用或期权变更。它只在 trace 完整且零失败时由严格报告器标记相应 `QUERY burst` 场景 `passed_p0`，不会影响其他 workload 的状态。

## 埋点契约与归因

所有时间戳均为同一进程的 `perf_counter_ns()` 单调时间。主动调用依次在入口、准入完成、命令持久化、binding 调用前、binding 返回、原生 callback 入 ring、归一化事件持久化和策略 ACK 处记录 `C0` 至 `C7`。对于原生 callback 驱动的场景，callback 入口为 `C0`，最小副本成功写入 ring 为 `C5`。

除时延直方图外，每轮必须上报下列白名单指标：

- `callback_ring_depth`、`worker_queue_depth`、`journal_queue_depth`、`journal_durable_lag_ns`；
- `process_cpu_millicores`、`process_rss_bytes`、`gc_collections`；
- `dropped_callbacks`、`rate_limited`、`native_error_count`。

这样可区分柜台响应慢、SDK/binding 阻塞、callback 入队瓶颈、journal 慢、worker 堆积和策略客户端 ACK 慢。任何队列溢出、未解释 callback、审计断链或 `CALL_STARTED` 后自动重发均视为失败，不以低延迟抵消。

### 同会话原生 SDK 与网关 A/B 归因

`gateway-ab-order` 用于回答“本地网关是否已成为主要延时来源”，但不替代全矩阵性能验收。它只允许在已武装的模拟盘 mutation fixture 上运行，并在**同一主机、同一账户、同一个活跃 EMT 会话**中，低频串行交替执行原生 `InsertOrder → CancelOrder` 和网关完整 `InsertOrder → CancelOrder`。

| 路径 | 必须统计的阶段 | 解释 |
| --- | --- | --- |
| `native_direct` | `C0→C4`、`C4→C5`、`C0→C5` | 原生 Python binding 的同步返回与首个匹配 EMT 回调到达；不经过网关 command/event journal 或 ACK。 |
| `gateway_full` | `C0→C2`、`C2→C4`、`C4→C5`、`C5→C6`、`C6→C7` | 分别覆盖命令持久化、调用/返回、EMT 等待、事件持久化和 ACK。 |

每段均输出 `count`、`p99_ns`、`p999_ns` 和失败数。`native_direct` 不具备 `C0→C2`、`C2→C4`、`C5→C6`、`C6→C7`，必须在报告中标注 `not_applicable`，不得写为零。报告还会按同周期、同接口给出 `gateway_full - native_direct` 的 `C0→C4` 和 `C0→C5` 观察差值；由于两条路径仍是顺序执行且 EMT/网络存在波动，该差值只能用于定位和趋势判断，不能宣称为单一组件的因果成本。

原生直调分支故意不写网关命令日志，只用于 A/B 参照；任何直调发送失败、callback 超时或中断后，必须先以券商权威查询进行人工核对，禁止自动重试或直接重复运行。该 A/B 结果不计入 P0、全接口覆盖或发布 SLA 门禁。

## 执行步骤

1. 在项目 `.venv` 中生成执行清单：

   ```bash
   .venv/bin/emt-gateway-perf --driver runbook-template --output ./data/performance/plans/gateway/gateway-perf-runbook.json
   ```

2. 为每个场景填入无敏感信息的 `fixture_id`、负责人和说明；同时在受控配置中保存测试账号、标的与操作参数。当前 Python binding 缺失的 `CreditMarginAvlTransfer` 与 `QueryCreditMarginAvlTransfer` 先标记为阻塞项；69 个 callback bridge override 虽已覆盖对应回调名称，但由于不存在可触发它们的原生主动接口，相关真实场景同样不能称为验收完成。

3. 网关实现接入 `GatewayTraceCollector`，运行时仅输出 JSONL trace 到 `artifacts/performance/`。P2 已在 `emt_gateway/` 中完成订单/撤单的 C0–C4、native fastspi ring 的 C5、事件 durable 的 C6 和策略 ACK 的 C7 接线；每次运行独立设置 run ID，保持相同环境、SDK 版本、账户档案、负载和并发阶梯。生产压测应设置 `require_native_fastspi=True`，不能把 fallback 测量作为吞吐验收证据。其余 `QUERY` 接口使用 `query-fixture-template` 生成完整但默认禁用的本机参数清单；`gateway-query-fixture` 只接受启用的 `Query*` 项，并拒绝账号、密码、地址和 callback payload。`query-semantic-fixture-template` 另行生成当前消费者需要的空结果和分页配置：仅保存终态、非空数据对象计数与下一页整数游标，`gateway-query-semantics` 只有在语义断言通过时才归档 C0–C7 证据。

4. 生成严格报告：

   ```bash
   .venv/bin/emt-gateway-perf --driver gateway-trace-report --runbook ./data/performance/plans/gateway/gateway-perf-runbook.json --trace-input ./artifacts/performance/gateway-traces.jsonl --output ./artifacts/performance/gateway-c0-c7-report.json
   ```

   P3 的真实低频只读预检使用 `gateway-readonly`；它会要求原生 fastspi 并生成同一份 C0–C7 trace 报告。先对普通账户执行一轮，再扩展到信用和期权账户的共同查询集合。

5. 先用 `workload-plan-template` 生成并审查非稳态控制清单；再使用 `gateway-fixture` 校验 runbook 的每个 `fixture_id` 与 `owner`，以及非稳态清单的 control/recovery 引用。它默认 dry-run，只有显式传入 `--execute-simulated --fixture-command ...` 且提供完整清单时才会启动外部、已审查的模拟盘网关进程。该进程通过环境变量接收 runbook/trace 路径，账户、密码、地址、标的和业务参数仍只留在本地受控配置。

   对尚未具备可控 EMT 柜台事件源的回调韧性开发，可先运行独立的本地注入 runner。它不加载 SDK、不连接柜台、不使用账户，也不执行任何交易；仅把最小 callback 事实送入 `CallbackPipeline`，覆盖本地断连/重连通知、有限突发、重复到达、成对乱序到达、C5 后慢消费者、空查询终态和两页查询形状。默认使用 write-through `FileJournal` 与 native fastspi，以测量本机 C5→C6 持久化瓶颈；它刻意不声称 EMT 断线、柜台乱序、去重或消费者重排已被验证。

   ```bash
   .venv/bin/emt-gateway-perf --driver gateway-callback-injection --fixture-owner fengyu --callback-injection-iterations 100 --callback-injection-burst-width 4 --callback-injection-delay-ms 10 --output ./artifacts/performance/injected/gateway-callback-injection.json
   ```

   该命令的 trace 固定另存为 `gateway-callback-injection.injected.traces.jsonl`，首行带 payload-free 的 `artifact_classification`，报告中包含 `counter_performance_eligible: false`、`release_gate_eligible: false` 与 `must_not_merge_with_emt_trace_evidence: true`。正式汇总器会在计算 P0 前拒绝此类 trace；它们只能用于网关回调管线韧性开发，**绝不能**作为 `gateway-trace-report`、`gateway-workload-readiness`、`gateway-release-readiness` 或真实 EMT P0 汇总的输入；真实柜台证据与注入证据必须分目录归档。

   真实会话断线 fixture 使用本机 loopback TCP proxy，只关闭此 fixture 的 SDK 到柜台连接对，不修改防火墙、路由或其他应用连接；正常 `logout` 绝不视为断线。默认仅执行 1 轮，先确认 SDK 确实发出 `OnDisconnected` 及可能的 `OnConnected`，再由已审查的 workload plan 决定是否扩大样本。该 trace 是真实 SDK/native callback 与真实柜台连接的网关路径证据，但断线触发点在本机，因此不得把结果解释为柜台侧网络时延或供应商重连 SLA。

   ```bash
   .venv/bin/emt-gateway-perf --driver gateway-session-fault --sdk-root ./EMT_python_SDK/emt_api_python --accounts-file ./data/performance/config/emt/emt-sim-accounts.json --profile ordinary --fixture-owner fengyu --session-fault-cycles 1 --session-fault-timeout 12 --output ./artifacts/performance/real/gateway-session-fault.json
   ```

   2026-08-26 的一轮 loopback proxy 预检未建立 proxy TCP 对，SDK 在到达代理之前即会话启动失败，因而 `OnDisconnected`/`OnConnected` 均为 `pending`、不产生任何 P0 样本。SDK 自带 `tradertest.py` 也明确：用户主动 `logout` 不触发 `OnDisconnected`，断线后 API 不会自动重连。经当前决策，真实断线阶段正式保留为 **external-fixture blocker**：缺少 SDK 可接受且按单连接隔离的外部流量控制入口（例如柜台侧测试代理或供应商的单会话断连控制）前，不再重试 loopback proxy，且不得以反复 `logout/login` 替代该证据。它不阻塞其他可独立执行的真实查询、订单归档和本地回调管线建设，但继续阻断相关 `CB-S reconnect/storm`、恢复和断线对账场景的 P0/发布验收。

6. 先达到每项 `passed_p0`，再在同一环境下完成发布样本量、稳态/突发/流控/恢复四组结果，并经批准后填充版本化 `performance-baseline.json` 的每条 C0–C7 路径 p99 预算。用 `gateway-acceptance-report` 对报告和批准基线求值。P0 和发布结果均至少重复三轮；任一轮异常需要解释并重新测试。
