# 测试与验收规范

## 1. 测试原则

- 任何 EMT 调用都通过 `native_api.py` facade。单元测试禁止依赖实盘或真实 SDK。
- 正确性优先于吞吐：崩溃点、乱序、重复、断线和慢盘测试必须纳入持续集成。
- 性能报告必须附带硬件、操作系统、Python、SDK、磁盘、配置、负载模型和原始直方图；不能只报单次平均耗时。
- 具体的 86/69 性能覆盖、测量边界与负载模型以 [EMT接口性能文档](./03-EMT接口性能/README.md) 为准；synthetic 压测只能验证网关/测试链路开销，不能替代测试账户的 EMT P0/P4 结果。
- 仿真/测试账户通过不代表实盘权限已开通。实盘灰度必须隔离账户、额度和策略。
- 可观测性是正确性的一部分：每个测试用例都必须断言其命令、回调、状态、投递与异常能够通过 `trace_id`/`correlation_id` 在审计账本、结构化日志和指标中关联；不能仅断言业务返回值。

## 4. 必测故障场景

| 场景 | 注入点 | 预期结果 |
| --- | --- | --- |
| 进程崩溃 | `COMMAND_PREPARED` 后、`CALL_STARTED` 前 | 恢复后从日志发射一次。 |
| 进程崩溃 | `CALL_STARTED` 后、`NATIVE_ACCEPTED` 前 | 状态为 `SUBMIT_UNKNOWN`；只对账，不自动重报。 |
| 磁盘异常 | journal flush 超时/失败 | 停止新订单，保留可读前缀和故障证据。 |
| 原生回调风暴 | MPSC ring 达高/硬水位 | 先停止低优先级账户查询/慢策略，硬水位 `DISARMED` 并全量对账。 |
| API 断线或服务端重启 | SPI 通知/请求失败 | `Logout → Login`，公共流重传与查询合并；未对账前不可交易。 |
| 柜台流控 | 返回 `211008` 或实测等价错误 | 窗口乘性收缩，返回 `VENUE_THROTTLED`，不重发既发命令。 |
| 迟到查询回调 | request ID 完成后到达 | 被 session/冷却窗口隔离，不能污染新请求。 |
| 自成交/重复回报 | 同一 `exec_id` 多订单或重复事件 | 按复合键去重，不丢真实成交。 |
| 日切 | 交易日变化/进程受控重启 | 归档、会话重建、公共流重传、对账后才放开。 |
| 审计管道失败 | audit ring 满、ledger 写失败、哈希链断裂 | 记录缺口、停止新单、进入 `RECONCILE_REQUIRED`，不采样或覆盖。 |
| 企微不可用 | DNS/超时/429/5xx/进程重启后恢复 | 原始 `WARN+` 仍写 JSON 日志与 outbox；通知至少一次重试、`alert_id` 可查、积压告警可见。 |
| 告警风暴 | 相同/不同指纹高频异常 | 每条事件保留；批量消息包含 ID 范围/计数；不阻塞 SDK callback 或发射路径。 |

## 5. 性能基准方法

分别记录并输出 HDR Histogram 或等价的可合并直方图：

```text
strategy_receive → journal_durable
journal_durable → InsertOrder_return
spi_callback_entry → ring_enqueue
ring_enqueue → event_durable
event_durable → client_ack
```

- 负载至少覆盖稳定速率、突发、不同订单键分片、账户查询竞争、资金/信用/期权回调、慢策略和流控边界；不设置行情负载，因为该服务不包含行情链路。
- 每一负载先 warm-up，再进行固定时段采样；报告 CPU、内存、GC、上下文切换、磁盘 fsync、网络丢包和队列水位。
- 仅在账户、SDK、OS、机器规格、配置与风险限制都相同的条件下比较版本；不能把仿真吞吐当作实盘容量。
- 任何队列达到硬水位、journal durable 失败、事件丢失或重复报单，即使平均延迟较低也判定失败。
- 监控/审计基准还须报告 FlowRecord 生产/持久化/导出延迟、日志写入失败数、AlertOutbox 积压和企微通知成功率；这些指标不可从性能报告中省略。

### 5.1 `MmapJournalProfileV1` 专项验收（新增，未通过前不得启用）

本节只适用于[定档](../01-架构与定档/04-OMS-EMS-Adapter-PaperBroker模块化实施方案.md)第 13.4 节的 Python mmap 热路径。历史外部 Journal 压测样本不得冒充通过。所有真实 EMT 变更仍仅可在受控模拟盘、`DISARMED` profile 和已批准的额度内执行。

`MmapJournalProfileV1` 的 C2/C6 表示“本机 mmap frame 完整提交，操作系统持续运行时重启进程可读取”，并不表示 SSD 已物理确认，也不表示可抵抗断电、内核崩溃、存储丢失或主机故障。下表中的“通过”不能被表述为跨主机 HA、自动恢复或账户 `READY`。

| 编号 | 场景与负载 | 必须验证的事实 | 通过标准 |
| --- | --- | --- | --- |
| MJ-01 | `MmapFrameV2` 编码、随机截断、CRC/长度/version 损坏与 commit-word 故障注入 | reader 只接受连续、完整、校验通过的 frame；半帧不能成为 `PRE_NATIVE`、`NATIVE_ACCEPTED` 或 callback 事实 | 10,000 个合成 frame 与每类故障注入均零误读；首个不连续/损坏处锁存 `JOURNAL_INTEGRITY`，不跳过、不补写。 |
| MJ-02 | 预发单/accepted/outcome/cancel 的每个 frame 边界崩溃 | `PRE_NATIVE` 必先于 EMT 副作用；`CALL_STARTED` 后结果不明时不自动重发；C6 前未完成 outcome 不能投递 C7 | 每个边界至少一次强制终止与重启读取；无重复 native 调用、无伪造 C7、无未知 in-flight credit 自动释放。 |
| MJ-03 | 300 条多订单 burst，至少 4 个固定 shard | 相同 `order_key` 始终进入同一 shard，且 frame 的 phase/事实顺序与 callback ingress sequence 一致；不同订单允许并行 | 300/300 identity 完整且无跨 shard 重复；专门生成的均匀 hash corpus 在每个 shard 至少 10%、至多 40%，以排除 hash/配置退化。 |
| MJ-04 | 外部数据存储未配置、对应 Unix socket 不存在 | 外部数据存储不在 C1→C2、C5→C6 或 C7 的同步依赖图；本地 Journal 是唯一热路径事实 | 300 条受控 EMT 模拟盘样本中 300/300 native accepted、300/300 C7、300/300 `C5→C7` 时间对，且无外部数据存储连接尝试、无 callback gap、无 producer/dispatch/callback error。 |
| MJ-05 | mmap shard 写满、lane/ring 满、route/merge manifest 校验失败、projector 长时间停滞 | 满载和完整性错误均 fail-closed，不丢 frame，不将已接受事实伪装为投影完成 | 新委托得到确定性拒绝或 `STOP_NEW`；既有可信前缀可读；无静默丢回调、无越过 C2 的 EMT 调用、无越过 C6 的 C7。 |
| MJ-06 | projector 恢复、重复启动和乱序读取 | SSD、PG 与未来 projector 只消费已确认 `MmapJournalPositionV2`，能幂等追赶并保留 per-order 因果 | 每个已确认 frame 最终恰好投影一次；重复投影不会新增业务事实；projector 结果不能反向改变 mmap 事实或释放 gate。 |
| MJ-07 | 进程 `SIGKILL` 后、操作系统保持运行的恢复演练 | 重启进程可扫描各 shard 可信前缀，核对 merge manifest 与 Broker 只读快照；未知调用保持对账 | 不自动重发、不自动 `READY`；任一 Journal/快照不完整时保持 `DISARMED + RECONCILE_REQUIRED` 或 `JOURNAL_INTEGRITY`。 |

性能验收以同一 Git revision、同一 SDK、相同账户/风险额度、相同 CPU 亲和性、相同 burst 形状和固定的 mmap shard 数为前提。先 warm-up，再独立运行 **3 轮 × 300 条**；每一轮均必须满足 MJ-03/MJ-04 的完整性条件。分位数采用 nearest-rank，原始时间对、队列水位、GC 状态、上下文切换、CPU/IRQ 证据和每个 projector 的 lag/position 都必须留档。

截至 2026-09-07，Git revision `93dabee` 已在外部数据存储 socket 故意不存在的隔离 Linux 模拟盘环境完成 **3 轮 × 300 条** `MmapJournalProfileV1` 闭环：每轮均为 300/300 native accepted、300/300 C7、300/300 `C5→C7` 时间对、0 callback gap、0 producer/dispatch/callback error，且 300/300 清理撤单调用获 EMT 接受。报告明确为 `MmapJournalProfileV1`，并显示外部数据存储未进入 `C1→C2/C5→C7`；因此 **MJ-04 标记为 `[x]`**（仅指该 mmap 300 条事实）。

## 6. 发布验收门禁

上线前必须同时满足：

1. P0 capability report 对当前环境有效，所有计划接口为 `supported`。
2. 关键单元、组件、故障和安全测试全绿，且审阅 `CALL_STARTED` 不重发属性的测试用例。
3. 仿真/测试账户完成 P4 压测与故障演练；基准阈值经风控和项目负责人批准。
4. 实盘仅以小额、白名单、单策略开始；全程有人值守、可手动断路、有明确回退和对账负责人。
5. 观察期内无未解释订单、成交、映射冲突、回调溢出或 journal 异常，才允许扩大范围。
6. 抽样选择命令、撤单、内部对账、断线与错误场景，能从 `correlation_id` 完整关联到审计链、结构化日志、告警 outbox、企微送达结果及最终对账结论。
