## L1：分段mmap核心

新增 `oms/segmented_fact_journal.py` 和受限运行文件/内核lease原语；复用旧4KiB frame编码与CRC/commit fence，旧文件格式保持原义。逻辑journal_id跨段稳定，LSN/batch ID递增，单batch不跨段。preparer创建并登记spare后才入ready队列，append仅做mmap激活、写body、最后commit word及有界队列交接。sealed扫描/flush/fsync/hash和manifest原子发布在维护线程。

独立模块验收覆盖：

- 至少1,000次切段及2,002条fact连续回读；prepared≤2、sealed等待≤3。
- 不齐整batch留尾后整批换段，重开后LSN连续。
- append线程在发生切段时不执行文件open/fsync。
- 磁盘预算耗尽时提交前拒绝，不删除已有段、不消费LSN。
- 第二writer、错profile、缺段、重复manifest索引、坏activation、坏commit和sealed hash不匹配均拒绝恢复。
- 撕裂batch的第一条成员也不会先被暴露给reducer。
- 子进程在写入并切段后`os._exit`，重新打开能找回已提交batch并继续LSN。

当前模块保留封段，尚无自动归档/历史回收；disk budget满时会明确背压，不能把它称为已能无限长运行。服务LONG_RUNNING门禁继续关闭，等待L2–L5组合完整。

冷索引使用单独worker持有SQLite连接，DELETE journal＋FULL同步，只作为已提交事实的可重建冷索引，不作为新单Journal fence，不使用WAL。新单内存负向探测不访问文件；可能命中时必须走有界异步精确查验。同key查验合并且waiter总数有界。冷结果和交接receipt包含带认证的代际/内容绑定，篡改、错owner、旧代负向结果和存储故障不能被解释为“新单可接纳”。数据库丢失或错误scope不自动初始化。

`RetainedOrderBook`是显式opt-in的有界live reducer，不替换现有BENCHMARK默认OrderBook。未决订单不可回收；只有完整终态、预留已释放且冷commit receipt验证通过才删除热order/dedup/预留成员。事件窗口按绝对计数保留，超出热窗口明确要求冷reader，不静默跳到最新。单订单事件容量另保留撤单/终态槽；冷重试返回原ID和已验证replay事件，冲突只写冲突事实，不再次冻结资源。旧的全历史bootstrap接口在此reducer上明确拒绝，避免把缺少cold-aware恢复的组合误开启。

### L3E：有界快照延迟请求lane与冷页回送（2026-10-19）

实现revision：`9b60636`、`d8ef701`、`c4cb063`、`0e4a4d0`、`56054e5`；最终公开接口测试revision为`3ee55a0115bc790e2de57897d850b1fb9af8b259`。每个独立代码/测试步骤均提交并push至`dev`，核验远端hash。

`ConsumerUnixServiceV2`新增显式opt-in的`deferred_read_workers`和`deferred_read_capacity`，默认workers=0，保留既有BENCHMARK同步路径；没有新增部署配置绕过LONG_RUNNING能力门禁。服务组装时可指定例如workers=2、capacity=32；后续完整LONG_RUNNING builder再统一接入，当前不是已启用的长期服务配置。

请求链路：

```text
reactor：SO_PEERCRED/解帧/请求schema/会话授权
  → 有界快照lane：文件打开及hash校验、页读取/编码、过期pin释放
  → 有界完成队列＋socketpair通知
  → reactor：当前会话授权、签名cursor/TTL/stream代际/live pin复核
  → 原有输出字节预算、partial write、消费者响应
```

仅允许`CreateOrderSnapshot`与`ReadOrderSnapshotPage`，且必须同时在listener composition已审查的parallel-read白名单内。创建快照是有界投影/capability操作，不是交易提交；SubmitSignal、CancelOrder和CreateReplayPartitions不得进入这个队列。GetOrder、审计及PollEvents冷热reader尚未借此自动开启。

关键约束：

- worker数1–16；capacity同时计算排队、执行中和已完成但尚未回送的任务，不只是线程池等待队列。capacity≤1,024，且`capacity × MAX_FRAME_BYTES`不得超过服务输出预算；默认64MiB输出预算下不能配置1,024个最大响应槽。每个完成响应受单帧1,048,608字节上限约束，现有页大小/编码预算继续生效。这是响应槽预算，不是整个进程RSS证明。
- 队满在执行handler前返回可重试`RATE_LIMITED / READ_BACKPRESSURE`，不退回同步执行、不无界排队。worker只通知专用唤醒socket，不读写客户端socket；selector无任务时正常休眠，不以持续自旋等待磁盘。
- 每连接只保留一个未完成响应；后续已收到的帧须等前一响应完整发送后再调度。客户端断开/超时不触发读取重试，更不触发任何重复订单提交。
- worker持有私有trace副本，完成后才由reactor唯一producer发布；记录enqueue、worker-start、handler/encode、delivery、send时间对，不记录原始请求ID、cursor或业务敏感数据。普通worker异常返回脱敏`INTERNAL_ERROR`；线程内SystemExit等也必须完成token，不能留下永远等不到的drain。
- 回送前重新校验会话epoch；快照成功结果还须通过cursor签名/key、TTL、账号/scope、当前stream generation和live pin核验。代际/TTL失效返回合同错误，不交付旧数据；授权撤销关闭连接。该最终fence不读文件、不触发过期回收。
- source.close可能等待正在读取的文件锁。所有过期/容量/关闭路径均在索引锁外关闭source，避免reactor的内存fence间接等待磁盘；创建快照也进入worker，不能把hash校验或过期close留在reactor。
- 停机先停止接纳，保留会话/文件及managed组件直到reactor完成读任务屏障，然后统一关闭。即使完成队列已被取空，delivery阶段也不能提前关闭后端。默认5秒drain超时是明确生命周期失败，不伪报成功，也不宣称Python线程可强制取消任意阻塞I/O；该失败须由服务supervisor处理。

### L3I：原始Journal校验的公开冷审计（2026-10-20）

实现提交：`b981060`增加有界审计定位计划及Journal原文重放校验；`b8b1712`将GetOrderAuditTrail接入公开read lane与最终权限fence；`7e54bf998bfd2903a606be07270ac32da99eea28`补充审计索引/Journal校验trace。各独立步骤均验收、commit、push到`dev`并核验远端。

本接口沿用原Consumer V2的`GetOrderAuditTrail(oms_order_id)`及ConsumerAuditTrail响应：返回订单规范化生命周期事件的audit_id、OMS/execution ID、Journal ID/LSN及action指针。与原热OrderBook行为同口径，**不是全部原始SDK、账户、风险决策或幂等冲突事实清单**，不新增交易/恢复授权，更不证明EMT查询或掉电恢复权威性。

路径：

```text
GetOrderAuditTrail → 现有身份、schema、订单归属授权
  → 有界read worker → 采样已提交源水位，要求索引已覆盖
  → 同一SQL快照复制单订单checkpoint和有界物理batch hints
  → 释放SQL事务/连接
  → 从原始Journal只读映射逐batch读取
  → activation／完整成员／LSN／CRC／commit／规范化摘要校验
  → 既有OMS单订单恢复归约 → 与索引checkpoint的完整状态/事件比较
  → 构造既有审计指针 → 健康、scope、generation、授权最终fence → 交付
```

设计与容量：

- SQLite只用于定位，不直接作为审计权威。每个batch附带带校验和的`JournalTailCursor`位置；`order_audit_plan`按`order_facts`及batch主键索引查询，仅复制目标订单。错位、重复/遗漏状态batch、坏摘要、错scope/订单/执行ID、回放结果不一致都拒绝。
- verifier在只读worker中回读原始4KiB frame及完整batch，复用已实现的恢复状态机；不以自写的弱状态机拼接动作。原文件不存在/CRC损坏时，即使SQL库仍健康，也不能返回“审计成功”。输出与热OrderBook规范化事件序列一致；事实副本、latest和consumer事件缓存不能替代原文件。
- 默认单订单最多128个batch、512条fact、64个规范化事件，checkpoint≤256KiB；超过上限报错，不截断后宣称完整。单batch最多256条fact，原文读取按batch释放；512条事实frame基础量约2MiB，另有前驱/首成员重复校验、header及映射成本，不能当总IO上限、进程RSS或吞吐证明。底层scope SQL、文件映射及重放只发生在有界read lane，不加入append热路径。
- 冷审计同时覆盖热订单：RetainedOrderBook账号级事件窗口可能已裁剪，不能用当前窗口冒充完整订单历史。配置cold_order_reader时审计统一走Journal校验。冷订单归属查验允许GetOrderAuditTrail自己的只读上下文；CancelOrder仍无该上下文，不能打开冷SQL或借读模型发起副作用。
- 源/索引故障、滞后、校验失败及审计交付前投影失效，返回既有`AUDIT_EVIDENCE_UNAVAILABLE`（同帧可重试），不返回部分audit_trail。错授权epoch不发送旧数据。完整性不足不是“没有历史”，不得降级成空成功。
- reader/stream/epoch最终fence仍不读SQL或Journal。没有开放新客户端字段、没有变更签名cursor或Consumer schema。GetOrderAuditTrail须同时进入硬编码只读集合和实例parallel_read白名单，且service配置read workers/capacity；默认BENCHMARK组装未自动启用。
- 新增`audit_index_started/finished_ns`（含连接及水位/定位协调，不是纯SQL时间）、`audit_journal_verify_started/finished_ns`（物理读取＋重放），以及batch/event数量。沿用enqueue、worker、delivery、send时间点；不记录账户、订单号、cursor或事实内容。

**读索引格式升级**：SQLite `user_version=2`，`batches`新增anchor及其摘要，和latest/事件/事实/cursor同事务写入；元数据DTO仍保持其原独立版本。旧`user_version=1`或缺字段的库明确拒绝启动，需要从保留的权威Journal重建到新的空私有目录，不自动ALTER、删除或初始化旧目录。不得直接覆盖旧读索引；该变化不涉及PG schema、原Journal frame或线上服务数据库。本轮验收只使用独立临时fixture，没有执行服务器业务索引重建。

- 若启动过程中源推进，拒绝固定cut，不返回旧/混合水位book。读取只遍历到采样J，不在有持续新写入时无限追赶。上一份coverage在新发布成功前不覆盖；部分冷copy、完整冷copy但未发布或进程退出均只留下未生效工作代。
- 索引是派生数据：旧派生库丢失时仍从必需的完整Journal重建新代，不能新建空冷库直接开始接纳。身份/源manifest缺失、源CRC/缺口、错scope、未来水位、坏metadata、错代目录或预算耗尽均明确拒绝。源不完整不能靠旧索引或旧active checkpoint补成成功。
- `checkpoint_recovered_state()`只返回本次未变动启动cut的已写active文件；已进入热book的live路径或源推进后拒绝，不对活跃writer做全量编码/fsync。空Journal的active文件为null，其余为带统一J的active-only checkpoint；全终态时orders/events为空但J非零。ColdAwareRecoveryStats仅描述本次启动cut，不是运行中新鲜度/余额/READY证书。

资源与生命周期：

- 复用policy的活跃订单上限、replay_cache_events和Bloom预算；默认最多64个账号、每订单64事件、active checkpoint编码64MiB。恢复订单页最多32行且合计1MiB，单订单checkpoint≤256KiB；终态归档逐条等待有界worker完成。新恢复器不会把所有终态订单对象同时装进OrderBook。
- active编码预算、最近事件条数及账号数均有硬门禁；这不是6GiB进程RSS证明。JSON解码/对象放大、源Journal/catalog启动扫描、SQL cache及重复编码需要在大数据资源采样中测量；不能以40个终态样本推算千万级恢复性能。
- ColdIntentIndex增加SQLite主体page上限，默认每个DB 8GiB；派生读库亦8GiB。每次创建新工作代，默认最多8代，失败代也计数，满后明确拒绝并要求受控维护，不自动删除旧文件。数据库主体最坏合计128GiB，另有active checkpoint、DELETE回滚、临时文件等，不等于已经落实了文件系统总配额或满足十二小时容量。
- 无自动代回收、源归档或cache复用；因此本包不承诺无限次重启或无限长留存。后续L4须实现校验、保留/回收及与archive reader的协作，不能直接解除代数门禁。
- 关闭先阻止冷查验/归档并drain，再关闭Journal及身份lease。资源关闭失败会显式失败，身份lease不提前释放；需由supervisor处理未排空的进程。ColdIndex和分段Journal的close可在drain失败后重试，不因“已开始关闭”伪报已释放。
- coverage摘要只绑定本次诊断/发布内容，不是EMT权威证书、HA证书或掉电持久性证明。mmap原文未承诺同步物理刷盘；机器掉电导致源低于已发布水位时拒绝，而非自动续交易。
