# OMS 持续饱和上限实测报告（2026-09-08）

> 结论：在 saturation revision `bf2bc93` 与低并发基线 revision `236acab`（仅新增压测工具，不改变 OMS 执行路径）、四个独立 OMS Python process、固定服务 CPU 与固定 client CPU 的环境中，不能用一次短跑给出“理论无限上限”。本报告给出可复验的**60 秒实测持续容量**、首个失稳点、上下界以及串行热态延时。
>
> 本轮仅使用合成脱敏 fact 和 seed snapshot，不导入 EMT SDK、不调用 EMT 接口、不发送任何委托；结果只代表 OMS HTTP/actor/snapshot 旁路。

## 1. 判定口径

每个有效档位均使用 k6 `constant-arrival-rate` 连续运行 `60 s`。只有同时满足下列条件，才计为“持续通过”：

1. 已完成速率等于目标（容许计时细小差异）；
2. `dropped_iterations = 0`；
3. `http_req_failed = 0`，业务 check 全部成功；
4. 原有性能门禁成立：
   - fact：P95 `<50 ms`、P99 `<100 ms`；
   - snapshot：P95 `<25 ms`、P99 `<50 ms`；
   - 混合：fact P95/P99 `<75/150 ms`，snapshot P95/P99 `<40/75 ms`。

“完整受理但高尾延时”单列，不能升级为门禁容量；出现任一 dropped iteration 或请求失败，即认定已进入饱和/失稳区。

服务端为四个 `--scopes 1` 进程，分别固定在专用 CPU；k6 固定在另一组 CPU。每个写入档位前通过受保护的 `reset-benchmark` 恢复相同的 seed baseline，并重置 HDR 指标，避免前序合成事实增长污染结果。

**fact 结论**：当前可作为发布门禁的持续容量为 **2,000 TPS**；观察到的“全量受理但不满足尾延时门禁”上界为 **2,750 TPS**；硬饱和开始于 **2,750–2,900 TPS** 之间。写入状态持续增长时，后台 immutable snapshot materialize/publish 与 Python 调度/内存回收会放大尾延时，因此不能使用此前 20 秒的 4,500 TPS 短跑值。

## 4. 同时读写（混合）60 秒结果

混合测量需要为两个 arrival-rate scenario 设置足够、但不过量的预分配 VU。过量 VU 会引入 k6 自己的 idle connection/调度失真；不足则会出现启动期 dynamic-VU dropped iteration。因此下表只把符合完整性口径的档位作为有效容量证明，并保留失稳档位作为边界证据。

| fact TPS + snapshot QPS | 已完成量 | Dropped | HTTP/业务失败 | fact P50/P95/P99（ms） | snapshot P50/P95/P99（ms） | 判定 |
| --- | ---: | ---: | ---: | --- | --- | --- |
| 2,000 + 2,000（400+400 VU） | 240,001 | 0 | 0 | 0.491 / 26.556 / 138.260 | 0.212 / 8.989 / 68.402 | **有效通过，4,000 ops/s** |
| 2,000 + 4,000（500+500 VU） | 359,977 | 24 | 20 snapshot | 0.449 / 41.737 / 148.237 | 0.278 / 14.900 / 74.034 | 首个失稳；不可计通过 |
| 2,000 + 5,000（500+500 VU） | 419,538 | 462 | 8,044 snapshot | 0.406 / 51.266 / 187.476 | 0.249 / 21.042 / 107.093 | 明显失稳 |

**混合结论**：在本轮已验证口径下，可明确证明的持续混合容量是 **2,000 TPS + 2,000 QPS（总 4,000 ops/s）**。在 **2,000 + 4,000（总 6,000 ops/s）** 已出现首个 dropped/失败，故当前混合饱和起点在 **4,000–6,000 ops/s** 间；不可将单项 `2,750 TPS` 与 `9,500 QPS` 相加为项目混合上限。

## 5. 单笔低并发真实热态基线

### 5.1 口径

此项测量补足“正常低并发调用”的数据，不复用吞吐压测的 percentile。客户端在独立 CPU 上运行，先对每种操作预热 `1,000` 次，然后通过四条**持久 HTTP 连接**轮转发出 `10,000` 个样本；全程全局一次仅有一个 request in flight，未发生自动重试。计时边界是客户端 `HTTPConnection.request()` 前到收到并读取完整 HTTP response 后，故包含真实 TCP/HTTP、服务端 decode/route、actor acknowledgement 或 snapshot JSON response 及调用方 Python 调度。

它不是 EMT `C0→C7`，也没有调用 EMT SDK；它只证明当前 OMS HTTP/actor/snapshot 旁路在热态、单笔、低并发下的延时。

### 5.2 端到端热态结果

| 操作 | 样本 | P50 | P95 | P99 | P100 | 语义 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| fact-ingest `POST → 201 PROJECTED` | 10,000 | 0.166771 ms | 0.199299 ms | 0.298779 ms | 3.739914 ms | 已完成 HTTP decode、scope actor 校验和 projector 应用；使用 minimal acknowledgement response |
| immutable snapshot `GET → 200` | 10,000 | 0.099759 ms | 0.126910 ms | 0.154412 ms | 3.611700 ms | 已读取当前 immutable generation 并完成 JSON response |

P100 是一次性 OS/网络/调度离群值，不应与 P50--P99 的稳定热态混为一谈。四个 shard 的端到端 P99 范围分别为 fact `0.287852–0.302423 ms`、snapshot `0.133540–0.165308 ms`，没有单一 shard 主导尾部。

### 5.3 服务端内部 HDR 对照

内部 HDR 不包含客户端 TCP/HTTP 计时，因此用于定位而不是替代上表：

| 内部路径 | 每 shard 样本 | P50 范围 | P95 范围 | P99 范围 | 含义 |
| --- | ---: | ---: | ---: | ---: | --- |
| `admit → projected` | 2,750 | 35.231–36.383 µs | 39.967–55.679 µs | 70.015–72.063 µs | scope actor 已接受、校验并投影 fact |
| immutable snapshot lookup | 2,750 | 1.002–1.051 µs | 1.292–1.523 µs | 1.483–1.893 µs | 当前 immutable generation 内的 execution-id 索引查找 |

因此，低并发 fact 的约 `0.167 ms` P50 不能被误解为 actor 本身耗时：其中约 `0.036 ms` 是已测的 actor/projector 内部路径，余量来自真实 HTTP/client/server 编解码与调度。snapshot 的约 `0.100 ms` P50 同理，其中 map lookup 约 `1 µs`。

## 6. 为什么不将其称为跨环境“理论最大值”

压测只能给出受硬件、CPU 亲和性、内核网络栈、Python/uvicorn 版本、请求负载和 k6 generator 形状约束的经验上限。混合测试中已实测到：

- 过量默认 VU 预分配会产生大规模 `EOF/idle connection closed`，这是压测器连接池与调度失真，不能归因到单个 OMS shard；
- 降至按实际并发配置后，`2,000+2,000` 零错误通过；
- 在 6,000 ops/s，尽管失败量很小，仍必须按门禁判为失稳；在 7,000 ops/s 失败明显扩大。

因此，当前可用于工程容量规划的数字应采用保守的 **2,000 TPS、9,500 QPS、2,000+2,000 mixed**，而不是将短时峰值或单项上限相加。

若需要把混合硬上限从区间缩小到精确数值，下一步应使用两台独立 load generator（各自时钟同步），保留相同 k6 contracts、每个 generator 的 VU/连接数、TCP 重传/IRQ/上下文切换，并在 `4k → 6k` 区间以 `250 ops/s` 步长运行三轮 60 秒。那是对压测平台的扩展，不应伪装成已经完成的项目容量证明。
