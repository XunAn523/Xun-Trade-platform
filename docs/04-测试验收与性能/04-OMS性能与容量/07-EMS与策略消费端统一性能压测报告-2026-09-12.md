### 2.1 初始 S5 失败与修复证据

第一次 5 sidecar S5 尝试在 `9,000 rps` 下出现连接 EOF。服务端计数证明没有
`EmsPendingPlanBufferV1` overload、没有 planner worker error；每个 sidecar 继承的
`RLIMIT_NOFILE=1024` 才是根因。扩大为 10 shard、并仅将本次 sidecar 的本地 soft limit
提升至 `8192` 后，复验为 `360,007` 次请求、零 HTTP failure、零 dropped iteration。
平台 health 现公开 `open_file_soft_limit`，runner 默认将小于 `8192` 的 Linux sidecar
直接判为 E0/S0 preflight 失败；这不改主机全局限制，也不进入 EMT 热路径。

所以联合 profile 的最终状态为 `FAIL`，即使 OMS 和 E/S 部分自身均通过。随后停止本次 15 个
loopback sidecar 后，使用同一 revision、同一 SDK/fixture/scope/CPU 运行独立 499 baseline，
得到同样的 `499 native accepted / 0 C7 / 0 pair`。失败后两次权威 query-only 均为零未完成，
因此没有用本地 inflight 计数替代 EMT 权威清理判断。

## 4. 归因、限制与下一次复验条件

当前服务器日期为 `2026-09-12`（周六）；最后一次完整 W7 通过证据为 `2026-09-11`，并使用相同
执行 driver、scope 数、CPU 计划、SDK 参数和 fixture。两次 burst command 的唯一计划参数差异为
`--trading-day`。这是“仿真订单在当前场地时段没有发出回调”的强运营相关性，**不是** EMT
厂商对回调完成语义的证明；不能凭周末日期推断场地的真实原因。

下一次复验必须在 EMT 模拟盘已确认可产生订单 callback 的交易窗口进行，并按以下顺序：

1. 在当前 Git revision 先运行 query-only preflight，要求 complete 且未完成 `0`；
2. 先运行无旁路的 `EXEC-BURST 499`。只有 `499/499 C7`、完整 C5→C7 pair、terminal cleanup
   为零时才继续；
3. 重新启动受控 OMS/EMS/策略 sidecar，确认 `nofile >= 8192`、CPU 与 k6 管理地址隔离；
4. 再执行完整 `OMS-W7-EMS-STR`，保留所有 k6 summary、每 shard HDR、EMT 原始 payload-free
   时间对和 pre/post query-only proof；
