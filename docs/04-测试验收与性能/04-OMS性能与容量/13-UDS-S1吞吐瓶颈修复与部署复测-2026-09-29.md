## 2. 定位结论与修复

原结构把连接交给 16 个阻塞 worker。OMS 修改请求再通过共同的 dispatch lock 串行执行；
回复后 worker 继续等待同一连接的后续帧或 EOF。在高连接周转率下，socket I/O、GIL、
worker 切换、串行 dispatch 和客户端关闭等待叠加，降低业务处理效率。入口队列满是结果，
扩充队列会增加等待时间，不能证明容量增加。

当前无 Adapter composition 改为单 owner 的非阻塞 request reactor：

1. selector 完成 accept、读取、半包等待与部分响应写出。
2. 完整请求进入有界就绪队列，每个调度轮次最多处理 64 笔。
3. 同一连接仅保留一个待发送响应；流水请求依次执行，保持单连接顺序。
4. 继续调用原有 XTC2/CRC/schema、会话授权、OMS 幂等/风险/预占、mmap commit 和回执代码。
5. Journal commit 成功后才能返回 ACCEPTED；没有批量预确认或省略业务逻辑。
6. 未完成首帧容量 4096，就绪请求容量 2048，总连接上限 6144；首帧绝对超时 5 秒，
   已建立连接读写无进展超时 5 秒。背压回复保持有界。
7. 模式只在当前本地无 Adapter request composition 显式开启。配置了 live subscription
   的 listener 不能启用此模式；原 worker transport 保留供其他组合使用。

请求数量上限、principal 校验、会话 epoch 检查与无响应未知结果语义不变。
保留日志字段 `worker_queue_wait_ns_*` 以兼容采集器；在 reactor 模式含义为
“完整请求就绪 → 开始执行”。`ready_frames` 包含首次就绪后被拒绝的连接。
