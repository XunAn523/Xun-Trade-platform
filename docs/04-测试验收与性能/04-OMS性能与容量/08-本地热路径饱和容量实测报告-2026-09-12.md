# TradeCore 本地热路径饱和容量实测报告（2026-09-12）

> 结论：在当前固定 Linux 拓扑中，已由三轮独立、完整的 30 秒 plateau 认证的本地热路径
> 可持续能力为：策略信号→EMS admission **11,000 TPS**；合成 contract event→策略
> checkpoint/state apply **14,000 event TPS**；策略 immutable snapshot 完整往返 **10,000 QPS**。
> 三项是不同路径，不能相加。它们不包含 EMT SDK、`InsertOrder()`、场地 accepted 或 native
> callback，绝不能写成 EMT 报单 TPS。H1 已观察到 12,000 TPS 的延时合同失稳；H2/H3 的更高
> offered-load 尝试受同机 k6 VU 调度抖动影响，因而**尚未证明硬饱和上限**，只能保守采用本报告
> 的认证可持续值。

本报告遵循[统一性能压测标准](../05-统一性能压测标准.md)的 `H1--H3`。运行不导入 EMT SDK、
不连接 broker endpoint、不会产生委托、撤单或账户查询副作用；`DISARMED` 状态不变。

## 2. 认证可持续值

“认证”要求每轮都满足：完整 offered load、`dropped_iterations=0`、HTTP failure 为零、检查项全通过，
且 k6 summary 中所有阈值均未越线。下表为每条已认证路径三轮的调用方端到端延时（ms）。

| 路径 | 三轮实际速率（/s） | P50（3 轮） | P95（3 轮） | P99（3 轮） | P100（3 轮） | 认证结论 |
| --- | --- | --- | --- | --- | --- | --- |
| H1-SIGNAL | `10999.488 / 10999.539 / 10999.436` | `0.281 / 0.271 / 0.267` | `1.865 / 1.746 / 1.882` | `8.415 / 9.234 / 9.983` | `124.838 / 112.067 / 143.129` | **11,000 TPS** |
| H2-EVENT | `13999.541 / 13999.469 / 13999.485` | `0.131 / 0.132 / 0.130` | `0.280 / 0.279 / 0.284` | `0.453 / 0.445 / 0.513` | `27.084 / 21.192 / 50.654` | **14,000 event TPS** |
| H3-QUERY | `9999.587 / 9999.550 / 9999.526` | `0.124 / 0.118 / 0.120` | `0.236 / 0.262 / 0.347` | `0.389 / 0.473 / 0.537` | `38.946 / 29.685 / 46.449` | **10,000 QPS** |

P100 是单轮最大值，不与其他轮池化；三轮仅并列报告。H2 的 P100 高于其 P99 不构成阈值失败，

## 3. 上界、失稳和无效探索

### 3.1 H1：存在有效的 11k–12k 提交路径边界

`12,000 TPS` 档完整提交、零 HTTP failure、零 dropped，但 P99 为 `70.751 ms`，超过 H1 的
`60 ms` 合同；故它是有效的延时失稳，而不是 generator 故障。

```text
认证可持续值：11,000 TPS
首个有效失稳档：12,000 TPS（P99 70.751 ms > 60 ms）
当前边界：11,000–12,000 TPS
```

这不是 EMT C0→C4A 上限；它只描述策略信号在本地 EMS admission 边界的容量。

### 3.2 H2：14k 已认证；16k 仍是发生器受限边界

`16,000 event TPS` 尝试出现 `265` dropped iteration，并有 k6 `Insufficient VUs` 证据；HTTP
failure 仍为零，P95/P99 也未越线。这无法区分为服务端饱和，因此不得将 16k 写为 H2 硬上限。

```text
认证可持续值：14,000 event TPS
16,000：generator-invalid（VU 枯竭、265 dropped），非服务端硬饱和证明
```

### 3.3 H3：10k 已认证；高档位不能认证

`16,105 QPS` 在一组探索中有两轮零 dropped，但第三轮出现 `241` dropped；另一独立运行又出现
`550` dropped 及 VU 枯竭。因此它不满足“三轮均 stable”，不能替换 10k 认证值，更不能据此给出
读路径硬上限。

```text
认证可持续值：10,000 QPS
16,105：generator-invalid / 不可复现，非服务端硬饱和证明
```

## 4. 结果解释与后续验证

1. 当前可用于容量规划的是 `H1=11k TPS`、`H2=14k event TPS`、`H3=10k QPS`，分别按各自的
   调用模型配置余量；禁止相加成“系统总吞吐”。
2. H1 的 11k–12k 区间是当前唯一已经排除 generator 枯竭的首个有效失稳边界。其优化优先级应是
   11k 以上的 loopback HTTP/JSON、Python event-loop 调度与 admission worker 批次抖动，而不是
   EMT 或 mmap。
3. H2/H3 的“理论硬上限”在当前单机、同主机 sidecar+k6 形态下尚未证明。要继续上探，必须使用
   至少两台独立 load generator（时钟同步、分别记录 VU/连接/CPU/IRQ/上下文切换），并把每台的
   actual offered/completed/dropped 独立归档后再合并。否则 k6 自身的启动/调度抖动会污染容量结论。
4. 任何更改 shard 数、CPU 集、VU/连接计划、k6 版本、协议、实现或阈值时均需新 profile，不能与
   本报告横向比较。真正 EMT 报单仍必须以 `EXEC-BURST` 的 C0→C4A、C5→C7、callback pair、
   cleanup 和当前每秒 500 笔场地约束单独验收。

## 5. 归档与清理

所有本次 loopback sidecar、k6 和临时 fault key 已停止/删除；端口 `18180--18189` 已确认不再监听。
保留的服务端工件仅用于重放指标判定，不包含敏感业务 payload。一次因人工中断留下的 k6 子进程已
促成 runner 的进程组清理修复；后续中断将写 `ABORTED` 工件并终止活跃 k6 process group。
