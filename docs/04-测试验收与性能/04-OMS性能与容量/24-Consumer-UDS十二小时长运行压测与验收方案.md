## 3 部署与资源冻结

正式服务、发生器和观测器分开运行。发生器只调用公开接口，不能拥有reset、删除Journal、调用OrderBook内部方法或直接写入状态的能力。运维编排器负责预检、一次启动、监控和安全停止。

使用多进程LONG_RUNNING候选入口时，systemd单元必须显式设置`KillMode=mixed`与足够的`TimeoutStopSec`（当前75秒）：先由主进程协调停止入口、Mock、读进程、投影及存储owner，超时仍清理整组。候选CLI会只读核对自身实际cgroup v2及所属unit的KillMode，配置不符时不创建runtime。最终必须核对runtime关闭后生成的`*.lifecycle.json`，其绑定闭合status/source manifest SHA且证明owned child退出码均为0；仅有早于存储关闭的status或systemd `Result=success`不足以通过。

## 4 十二小时混合时间线

使用服务器单调时钟设共同`T0`，周期`i`为`[T0+i×600s, T0+(i+1)×600s)`，`i=0…71`。阶段按绝对时间触发，不等待上一阶段排空，不因发生器迟到延后时间线。预热、初始20万条订单和初始快照建立在T0之前完成并单列耗时。

下表速率分别适用于SubmitSignal和热快照页查询。L组为低频组，H组为高频组，F组为多个合法消费者/策略流。L/H/F/B仅出现在客户端证据，不向服务器发送测试优先级。

| 周期内区间 | 阶段 | 每种操作的计划负载 | 观察内容 |
|---|---|---|---|
| 0–60s | IDLE | 不新增业务调用；保留已建立连接及正常维护 | 缓存、FD、内存同相位基线；空闲后首请求 |
| 60–120s | LOW | 1/s、10/s、20/s各20秒 | 单笔、低并发及低负载抖动 |
| 120–150s | RAMP | 20/s线性升到2,000/s | 升压时队列与调度响应 |
| 150–270s | HIGH | L=20/s＋H=1,980/s，总计2,000/s | 目标吞吐与同窗低频组延迟 |
| 270–390s | STEP | 20/s保持30秒→2,000/s保持30秒，重复两次 | 压力突变、排空及降压恢复 |
| 390–450s | FAIR | 20个F流各10/s＋H=1,800/s | 每流进度、公平性与授权隔离 |
| 450–510s | BURST MIX | 背景仍为L=20/s＋H=1,980/s；叠加下列三批 | 背景不中断及同时释放 |
| 510–600s | RECOVER | 停H，保持L=20/s | 排空、低延迟恢复及至少60秒稳态观察 |

三个额外突发分别为：

1. 450s共同释放2,000 SubmitSignal。
2. 470s共同释放2,000 ReadOrderSnapshotPage。
3. 490s同一barrier释放1,000 SubmitSignal＋1,000 ReadOrderSnapshotPage。

所有突发frame事先准备，barrier释放后开始建连；不创建2,000个线程，不把突发平滑成匀速，不暂停背景H组。分别保存各操作及联合整批墙钟。

RAMP按累计计划量生成：局部时间`t∈[0,30]`秒，累计请求数`N(t)=floor(20t+33t²)`，因此每种操作该段恰好30,300次。以累计差值发放预算，避免现有“每10ms必须整除100”的限制错误处理1/10/20/1,980速率。

每周期每种操作的计划计数为：LOW 620、RAMP 30,300、HIGH 240,000、STEP 121,200、FAIR 120,000、BURST背景120,000及额外3,000、RECOVER 1,800，合计636,920次。72周期各为 **45,858,240次提交、45,858,240次热页查询**，不含T0前seed和独立辅助请求。

12小时共216个突发barrier、432,000个额外突发请求，其中提交216,000次、查询216,000次；这些已包含在上述总计中，不能再重复加总。

## 5 持续轨道与mock生命周期

`LR12-STEADY`不执行IDLE/LOW/STEP，每种操作始终为L组20/s＋H组1,980/s，总计2K/s，持续43,200秒。纯持续轨道不额外叠加突发，其目标各为86,400,000次提交/热页查询。要另加突发时必须使用独立profile并重新计算总量。

两轨道都必须使用确定性、可复算的mock生命周期，不能让数千万订单永远ACCEPTED并常驻内存。候选资格配置为：每笔先正常Journal-first接纳，专用mock执行边界在1秒内产生合法终态；以测试序号确定80%完成、20%拒绝，映射和状态转换仍走实际reducer。冻结实际实现及每类产生的fact/event数。正式过程中不注入未提交的“假完成”，也不由发生器直接删订单释放资源。

资格测试必须证明该mock profile没有真实柜台调用，并确认它确实覆盖执行模拟、成交/拒绝及资源释放；当前`disabled-no-dispatch`入口本身不具备上述生命周期，不能当成已实现。

若通过公开CancelOrder补充撤单测试，单独标记该操作TPS、额外fact/event数和延迟，不计入2K SubmitSignal数量；不得把提交后撤单的最终耗时当作提交响应耗时。

所有“新单TPS”使用新业务幂等键，不能靠反复提交旧键维持TPS。每分钟另行选择历史/近期键做幂等和冲突抽查，明列为附加载荷；不得给同键换ID后冒充重试。未完成订单达到maximum_active_orders的专门边界场景在正式12小时前独立验收，不与正常2K轨道混算。

## 6 事件消费与查询口径

事件消费目标随实际事件生产量调整，最低能力为2,000 checkpointed event/s。若每单产生接纳和终态两个事件，HIGH阶段约需4,000 event/s；1批PollEvents取100条时约40次PollEvents/s，而不是4,000次请求/s。

消费者按官方签发的分片cursor读取并持久化checkpoint，不改签名token、不自行拆LSN。每个已冻结高水位区间消费完后，通过公开接口取得下一组区间，核验交界连续。不能持续重读T0前的固定seed来声称消费跟上实时生产。

在IDLE阶段允许消费先前积压和进行checkpoint，但单独记录；IDLE不要求凭空消费2K新事件。正常高压消费lag不得持续上升，终态事件也应消费。按事件生产、唯一消费、重复投递、缺口、checkpoint lag分别计数。

热页QPS默认读取已发布、未过期的固定水位快照；按TTL正常取得后继快照。不能12小时复用已失效token，也不能静默只读最初20万订单而漏报后来订单的可查询性。

每30秒由独立低频辅助调用尝试建立新快照，严格single-flight，记录成功水位、创建耗时及projection lag；构建中按冻结退避重试，全部尝试进入辅助计数。每分钟抽查近期、已转冷和旧快照边界页，核验固定水位下集合不变且无缺口重复。每小时做一次有界流式全量审计，不在reactor构造全量Python列表。

20万规模快照创建P95≤1秒、投影延迟P99≤1秒仍是门槛。扩展到百万/千万级的完整历史快照须采用已验收的冷分页和字节预算；若这些规模不能满足已冻结合同，必须报告对应容量失败，不将查询偷偷改成active-only。

## 7 容量与存储预算

先在与正式相同的生命周期、trace full模式、查询及消费配置下测量至少30分钟，得到fact数/新单、事件数/新单、各类字节增长、checkpoint临时峰值与归档速率。预算计入seed、辅助抽查、生命周期、异常、索引、trace和发生器原始样本；共享同一文件系统时合并计费，不能把相同空闲空间重复分给多个目录。

下表只按现有4,096-byte frame计算，不包含上述额外空间，也不是实测存储量：

| 轨道 | 新单数 | 仅2条接纳fact的数量 | 仅接纳raw bytes | 若平均5 fact/单的raw bytes示例 |
|---|---:|---:|---:|---:|
| LR12-MIX | 45,858,240 | 91,716,480 | 375,670,702,080 | 939,176,755,200 |
| LR12-STEADY | 86,400,000 | 172,800,000 | 707,788,800,000 | 1,769,472,000,000 |

5 fact/单仅作敏感性示例，必须以实际mock/reducer测量值替换。持续轨道仅接纳数据就约707.79GB；生命周期可能让raw需求超过1.7TB。上一轮清理后的约1.1TB空闲不是本次容量保证，也不足以无条件容纳后一个示例。

开跑预检按以下规则放行：

```text
remaining_required = 热段峰值 + 已验证归档增长 + 冷索引增长
                   + trace及客户端原始样本 + 双代checkpoint
                   + 临时文件/并行归档的峰值 + seed及辅助开销
storage_reserve = max(64GiB, 所在文件系统容量的5%, 已冻结的更高运维底线)
available_bytes >= 1.25 × remaining_required + storage_reserve
```

这比当前runtime policy的4GiB最低空闲更严格；须在12小时编排/健康保护中实际落实。压缩率只能用同profile实测值估算，并保留未压缩最坏情况/偏离增长率的安全退出路径；不能用预期高压缩率伪造足够容量。

现有32GiB Journal/16GiB trace候选配额不自动代表能覆盖12小时。必须证明归档和可验证回收能保持在线配额，归档空间及带宽另行落实。full trace每条的实际字节乘以总请求数单独预算；禁止关闭trace、采样或把客户端样本全留RAM后仍声称全证据通过。

增量订单投影的候选SQLite读索引还会保存最新订单checkpoint、事件、事实副本及batch位置。其默认8GiB仅为组件验收中的数据库主体上限，不是十二小时容量配置，也不是额外免费空间；需实测每订单/每事件增长，再将主体、DELETE模式回滚文件峰值、冻结快照及构建临时文件合并计费。数据库page上限不包含这些临时/外部文件。当前没有读索引分区归档/回收，达到上限会明确停止投影；不得仅调大上限后宣称长期磁盘治理通过。Journal raw下限也不能代替这个合并预算。

T0前可按授权清理旧测试Journal；T0至终审之间禁止清空当前namespace。正式新段只有在归档完整性、checkpoint覆盖、冷幂等/回放引用及保留条件全部满足后才可退出热存储；不能沿用“旧Journal不保留”的授权删除本轮仍依赖的数据。不得在测量中执行reset。

## 8 延迟与吞吐验收标准

逐请求保留计划释放、实际调用开始、建连完成、发送完成、响应解码完成及结果校验时间。另关联服务端accepted、首字节、frame-ready、dispatch-start、handler各子阶段、send-finished；字段以真实埋点为准，缺字段记缺失，不能推测补齐。

分别报告计划释放到完成、call-start到完成、发生器排队、服务端接纳到发送完成、事件生产到消费checkpoint。区间可能重叠，不能相加累计指标，也不能用不同样本总体分位数相减推算链路。

| 场景 | 强制验收标准 |
|---|---|
| HOT独立资格 | 每轮10,000正式样本，三轮；全成功，固定多 frontend fresh-per-request 合同 P95≤1.50ms、P99≤3.00ms；P99.9/P100强制报告 |
| LOW提交 | P95≤0.30ms、P99≤0.50ms，无错误；按1/10/20 TPS分别统计 |
| LOW热页 | P95≤1ms、P99≤2ms，无错误 |
| HIGH全体 | 每个完整60秒高压窗口，计划及完成均达到120,000提交、120,000热页；零业务错误/释放错误，不用窗外drain补吞吐 |
| HIGH端到端延时 | 提交P95≤20ms/P99≤60ms；热页及消费checkpoint P95≤10ms/P99≤40ms |
| 高频背景中的L/F组 | 每流每操作P95≤10ms/P99≤20ms，无饥饿；每流offered与完成闭合 |
| 发生器 | call-start排队P99≤10ms，无未记录的跳过/迟发/补发；所有计划请求均入账 |
| 2K单类与联合突发 | 216批逐批全成功、整批<1秒；提交LSN唯一数等于本批新提交数，背景不中断 |
| 突发期间L组 | 无丢失/超时，单条等待<1秒；单独统计，不按普通LOW门槛冒充低压基线 |
| IDLE后首请求 | 每周期首条提交≤2ms、首条已发布热页≤5ms，72周期逐条核验 |
| RAMP/STEP平台 | 达2K后的每个完整10秒平台达到每种操作20,000计划及完成；切换瞬间样本完整保留 |
| 降压恢复 | 计划降压后1秒内旧业务队列排空；L组两种操作各在2秒内取得连续20个≤1ms响应，20个样本跨越时间也计入恢复时间 |
| RECOVER稳态 | 恢复达成后连续60秒满足LOW P95/P99，且全部发生在固定90秒RECOVER内 |
| 维护交叉 | 以上门槛保持，不屏蔽维护时段；checkpoint/归档/切段/GC/key轮换各单报尾延迟 |

连续高速窗口以冻结的绝对窗口与相应流量组计数，不拿上一窗口剩余结果、突发额外样本或辅助操作补足背景目标。时窗边界规则在资格测试前固化；任何未按时完成的样本继续保留并计入迟到/排空，不修改窗口后重算成成功。

按分钟、阶段、消费者、操作和每小时导出count、offered、completed、错误、P50/P95/P99/P99.9/P100及HDR。允许在同一个12小时run内合并相同阶段和档位，但不得跨LOW/HIGH/BURST混池。

P99至少1,000样本，P99.9至少10,000样本。MIX中1 TPS档每种操作共1,440样本，可计算该档总体P99，但P99.9标为样本不足；其每小时仅120样本，应保留逐条/P100，不宣称该小时有充分P99证据。

## 9 资源稳定与正确性标准

- 正常目标负载下`memory.current`的60秒窗口P99≤4.5GiB；包含突发/维护的全过程峰值≤5.1GiB；`memory.events`的max/oom/oom_kill相对基线无增长。不以没有触发6GiB硬上限代替内存稳定证明。
- 稳态增长率≤10MiB/小时。MIX以相同IDLE相位的内存中位数比较，固定使用第2–12小时估计斜率，首小时所有容量/SLO失败仍计入总结果；同时报告anon/file、PSS及驻留对象数量。稳态首尾同相位差≤128MiB。
- FD、线程、子进程、快照pin、事件缓存、在线订单和未归档字节均不超过冻结上限；每周期回落到其平台值，不随总订单量无限增长。
- 正常消费projection lag P99≤1秒，maintenance/backlog在下一周期前回落；归档、checkpoint与spare准备不得永久饿死。至少一次真实key轮换与一次mock交易日切换在测量窗口内完成且与HIGH或BURST相交，触发时间在T0前冻结；不改主机时钟、不伪装真实交易日日切证明。
- 无重复新单、重复资源冻结、越权跨binding读取、事实/事件缺口、LSN重用或未知副作用自动重报。完整性问题一票否决。
- 主轨道全过程主PID不变，无OOM、崩溃、异常重启或人为reset。预期模拟终态拒绝属于mock业务结果，不等于SubmitSignal技术失败；两者须分表计数。

## 10 监控与安全停止

服务、发生器和监控均需在SSH断开后继续由受控systemd任务运行。只管理本项目unit/cgroup，不重启服务器。测试unit在正式窗口出现进程退出时保留失败并停止负载，不自动反复拉起后拼接为连续12小时。

每秒采集服务及全部子进程CPU、memory.current/stat/events、PSS/RSS、FD/线程、队列深度/最老年龄、active/prepared/sealed段数、磁盘空间/IO、归档与checkpoint水位、GC停顿、trace drop、快照lag和消费者checkpoint lag；每10秒聚合，每分钟形成不可变摘要。采样器自身要有配额和有界文件。

| 触发条件 | 立即行动与结果 |
|---|---|
| 任意事实/事件完整性、越权、幂等错误 | 标记FAIL_CORRECTNESS，停新负载、保留证据，禁止自动重报未知订单 |
| OOM/服务退出/主PID变化 | 标记FAIL_RUNTIME，停止发生器，不自动补时重测 |
| memory达到5.1GiB保护水位 | 标记资源门禁失败并停止新提交/新大查询；保留消费和必要drain，不能等到6GiB被kill |
| 实际磁盘空闲低于reserve，或剩余预测不满足容量预算 | 标记FAIL_CAPACITY，停止新负载并安全封存；不临时删除当前事实/证据续跑 |
| trace任何drop、writer失败、证据写盘失败 | 全证据验收失败；只保留短诊断窗口，不继续产生无法验收的数小时负载 |
| 正常目标窗口出现明确背压/技术错误/吞吐门槛失败 | 标记该子项失败，不重试掩盖；采集最多60秒诊断后安全停止 |
| 连续5秒无已接纳请求或维护任务进度 | 独立watchdog确认后停止新流量，保存线程/队列诊断；不全局杀进程 |
| 发生器release error、OOM、日志满或CPU不足 | 标记INVALID_GENERATOR，不能据此断言TradeCore容量失败，也不能宣称通过；修发生器后使用新run_id重新完整执行 |

停止仅对本次测试进程生效。先停止新请求，再限定最多60秒排空已接纳请求与消费；超时后记录未完成集合，不强行写成成功。标准排空时间位于12小时测量窗外，不能补足窗口内TPS/QPS；12小时结尾按冻结规则单列自然尾部。

## 11 证据与最终对账

证据根使用独立run_id，逐段写出并生成SHA-256 manifest。所有文件及目录受限owner访问；对外只导出别名、请求hash、订单hash、序号、状态和时间戳，不导出账号、密码、证券、价格、原始cursor或委托报文。

```text
<run_id>/
  run-manifest.json
  preflight.json
  environment/
  client/                 分组逐笔时间戳和流式块索引
  checkpoints/            消费者持久消费进度
  server-trace/           连续trace封段与覆盖证明
  runtime/                每秒资源和维护事件
  metrics/                分钟 阶段 每流 每小时HDR与计数
  audits/                 唯一性 水位 预留 冷热与最终对账
  integrity/              文件hash与完整性链
  report.json
  report.md
```

发生器不能把12小时所有样本、响应体或唯一性set放在内存。按有界块写出时间戳和hash，唯一性/缺口采用离线分区排序或磁盘索引复核。查询保存条数和集合摘要，不把每个100条响应完整复制数千万次。详细耗时原始时间戳仍须可复算，HDR不替代原始证据。

终审至少闭合以下关系：

1. 各阶段计划数＝实际调用数＋明确发生器失败数，禁止未记录跳过。
2. 调用数＝匹配响应数＋明确发送前失败＋发送后未知/未响应；未知不计成功。
3. 新单成功数＝唯一业务幂等键数＝唯一OMS接纳ID数，LSN按各批次独立核验，不假定一单只占一个LSN。
4. 实际fact数与按操作/生命周期统计的放大闭合；所有batch完整、checkpoint不跨半批，归档与在线段范围连续。
5. 生产事件数＝最终唯一checkpoint事件数，无不可解释缺口；合法重复投递单列，不重复计吞吐。
6. 原始服务trace与客户端请求hash/结果逐条关联，覆盖率100%，full模式drop=0；接纳前连接拒绝另与ingress计数核对。
7. mock全部到达冻结终态、预留总额回到应有值，近期/冷历史订单查询和旧幂等重试正确；无真实Adapter副作用。

仅结束时的计数闭合不足以证明SLO，所有分钟、阶段、低频流和突发门槛仍须逐项通过。`PASS_LR12_MIX`、`PASS_LR12_STEADY`分开给出；资源或证据失败不得被总体吞吐均值覆盖。

## 12 故障演练与执行顺序

SIGKILL、磁盘满、损坏manifest、归档停顿、worker故障和不终结订单属于独立故障轨道，先在资格阶段验收或在12小时结束后使用独立run_id执行，不能故意在零中断主轨道强杀再称连续运行通过。

12小时结束后可用同一保留数据根做受控重启，验证持久身份、订单/预留/冷热幂等、cursor连续性和checkpoint后缀恢复。60秒恢复目标只对已经验证的“checkpoint＋最多5分钟后缀”规模生效；必须声明实际活跃订单、历史规模与后缀数，不能跳过未覆盖事实。该结果单独记为恢复验收，不代替EMT查询权威证明。
