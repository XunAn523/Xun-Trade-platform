# 统一压测口径定档标准

> 定档版本：`BenchmarkStandardV1.1-Frozen`
>
> 适用范围：所有 OMS、EMS、策略消费端、执行引擎、券商/交易所适配层及订单状态投影系统。
>
> 定档状态：本文件只定义最终、可执行的统一口径；历史运行结果、变更过程和性能比较必须存放在独立 evidence/report 中。
> 安全边界：通过任一 profile 仅证明该 profile 的受控环境事实；不自动证明生产 SLA、`READY`、自动恢复、跨主机高可用或场地性能承诺。

## 1. 目标、范围与禁止混算

本标准定义跨项目一致的测量边界、负载合同、完整性门禁、证据归档和通过语义。所有接入项目必须先建立不可变 profile，再执行压测；不得复制其他项目的批量大小、阈值、存储方式或历史数值作为本项目结论。

| 测试族 | 回答的问题 | 不回答的问题 |
| --- | --- | --- |
| `EXEC-BURST` | 固定宽度执行突发的本地提交、回报、完整性、清理和背压 | OMS/EMS HTTP 吞吐、券商或交易所生产 SLA |
| `EXEC-HOT` | 预热后的低并发单笔体验 | 突发排空能力、持续容量 |
| `EXEC-OVERLOAD` | 超过已知安全容量时的有界 admission、拒绝和恢复 | 超额请求全部成功 |
| `OMS-W0~W6` | OMS fact、投影、snapshot、watermark、背压与回放 | 场地委托性能 |
| `EMS-E0~E5` | EMS 计划接纳、路由、子指令、控制和查询 | 场地同步调用、成交或拒绝等待 |
| `STR-S0~S5` | 策略信号、事件消费、checkpoint 和查询 | 策略算法、行情计算或模型收益 |
| `H1~H3` | 本地热路径的可持续容量与首个失稳边界 | 券商、交易所或网络报单上限 |
| `STAB-L1~L2` | 持续负载、突发恢复和运行中故障的稳定性 | 跨主机容灾 |
| `W7` | 旁路压力下真实执行链路仍完整且无不可解释退化 | 不同主机/拓扑/适配器的横向性能比较 |
| `DR-H0~H4` | 声称 HA/DR 的项目的 RPO/RTO、切换和权威对账 | 单机 mmap 或本地缓存即具备 HA |

以下规则为强制要求：

1. `G4→G5` 是适配器、网络和场地的外部异步等待，只能直接报告；不得计入项目的两段内部延时。
2. 单笔 percentile、整批墙钟、持续吞吐和容量上限是不同指标；不得相加、相减或互相替代。
3. P95/P99/P99.9 只能由同一轮、同一 profile、同一边界的原始时间对计算；跨轮、跨 scope、跨主机、跨适配器或跨架构不得池化。
4. 缺失时间对、callback gap、未解释拒绝、清理未闭环、测试机饱和、环境预检失败或异常时，该轮不得标记为通过。
5. 所有 evidence 必须脱敏：仅保留样本序号、scope 序号、单调时间戳、阶段和结果分类；不得保留账户、标的、价格、订单号、client reference、密钥、IP 或原始 SDK 回包。

## 2. 通用 G0--G7 边界

每个项目必须在 profile 中登记下表的一对一映射。项目可增加子阶段，但不得删除、移动或用不同业务事实替代既有边界。没有原生场地回报的内部模拟或回放系统必须将 `G5` 标记为 `N/A`，并独立说明本地 outcome ingress；不得伪装为场地 callback。

| 边界 | 规范含义 |
| --- | --- |
| `G0` | 单笔真正进入执行系统；burst 另有共同释放时刻 |
| `G1` | admission 接纳，订单/指令已进入稳定 owner lane |
| `G2` | 副作用前本地可验证 durable fence 已完成 |
| `G3` | 即将调用适配器或原生执行 API |
| `G4` | 同步调用返回，且本地 accepted identity/mapping 已完成 |
| `G5` | 原生或场地 callback 首次进入系统观察点 |
| `G6` | outcome 的本地 durable fence 已完成 |
| `G7` | 下游可消费的 receipt/state/checkpoint 已完成 |

两段项目内部累计延时固定为 `G0→G4`（提交）与 `G5→G7`（回报）。`G0→G7` 是完整观察路径，包含 `G4→G5` 外部等待，不能写成项目内部延时。

## 3. 运行有效性前置门禁 `V0~V5`

任何压力或副作用测试必须先完成本节。任一前置失败只可标记 `BLOCKED`，不得以重试、缺样本或部分成功生成性能结论。

| Gate | 强制条件 | 通过证据 |
| --- | --- | --- |
| `V0-PROFILE` | Git clean、profile、驱动、fixture/order-plan、运行时、SDK/ABI、路由、CPU plan、容量和 durable-fence 语义均固定 | manifest、哈希和只读预检 |
| `V1-CLOCK` | 使用单调高精度时钟；记录时钟源、进程间可比性、共同 release 的实际 skew 和每个打点的采样开销 | clock calibration artifact；超出本 profile 声明 skew 上限即无效 |
| `V2-GENERATOR` | generator 与被测服务分离或等价资源隔离；最大 VU/连接/请求对象首请求前预分配；先完成空载和 generator 自检 | generator CPU、队列、连接、丢弃、网络和退出状态摘要 |
| `V3-ENVIRONMENT` | 权威未完成订单/指令为零，安全状态、ACL、scope ownership、route/manifest/capability 全部有效 | 无副作用 preflight 与权威查询摘要 |
| `V4-CALLBACK` | 对有外部 callback 的适配器，每个实际 scope 先以最小受控样本验证 `G5→G7` 可达，并确认原生桥接观察点有数据 | 每 scope 的 `G5/G6/G7` 覆盖、关联和受控清理证据 |
| `V5-OBSERVABILITY` | 打点、HDR、资源采集、错误分类和 evidence 写入均可用；以 instrumentation-off 对照证明采集未改变 profile 的通过语义 | 开关配置、采集完整性和对照摘要 |

`V4-CALLBACK` 的零 callback 只能说明“当前窗口未观察到 callback 到达本系统”；不得猜测为柜台、SDK、网络或本地路由的具体原因。`V4` 未通过时，后续真实 burst 一律为 `BLOCKED`，不得称为产品失败或性能退化。

## 4. 不可变 profile 与数据分布

每个 profile 至少包含以下内容。缺项的运行仅可作为探索性实验，不可用于回归、容量、发布或 SLA 讨论。

| 字段 | 要求 |
| --- | --- |
| 身份 | `system_id`、`profile_id`、`measurement_schema_version`、adapter/venue/environment、Git revision |
| G 映射 | `G0~G7` 对应的函数、进程、线程和事件边界；`N/A` 必须说明原因 |
| 拓扑 | scope/session/API 数、owner routing、调用并发约束、lane/ring 容量、进程与 CPU 归属 |
| 负载形状 | 共同释放、持续速率、ramp、burst、producer 数、预热和冷启动排除规则 |
| 数据合同 | 固定 seed、schema 版本、最小/典型/最大合法 payload、分页大小、均匀 key、热点 key/scope、幂等重复和非法输入比例 |
| 容量依据 | 场地流控、账户额度、适配器并发、风险 gate、硬水位与 backpressure 策略 |
| durable fence | `G2/G6` 的技术、提交语义、进程故障/掉电边界、完整性校验与恢复行为 |
| 判定线 | 完整性、延时、吞吐、批量墙钟、持续时长、容量和允许回归幅度 |
| 证据 | 原始时间对、HDR、环境、fault、preflight、cleanup、资源归因和 SHA-256 归档位置 |

所有性能 profile 至少运行三轮独立样本。默认以“每轮同一 percentile 的中位数”汇总，必须同时保留三轮逐轮值和最小/最大范围；不得将所有轮次样本合并后重新计算 P95/P99。

## 5. 计量、统计和资源归因

1. 所有延时使用 `ns` 级单调时间戳保存，报告显示 `ms`。跨进程只可使用同一主机可比较的单调时钟；跨主机延时必须有 PTP/NTP 偏差、同步状态和误差上限，未达标时只能报告本机分段。
2. 每个强制区间输出 `count / P50 / P95 / P99 / P100`，使用 `nearest-rank: rank(q)=ceil(q×n)`，`P100=max`。
3. 对持续型 `W`、`E`、`S`、`H`、`STAB` profile，当有效样本不少于 10,000 时，额外输出 `P99.9`；样本不足则明确记为 `N/A`，不得用 P100 代替。
4. 每轮记录每 scope 的 queue/ring 高水位、inflight、拒绝/过期/异常分类、gap、重复、乱序、consumer lag、GC、CPU 时间、迁核、上下文切换、minor/major page fault、IRQ、内存、磁盘和网络丢包。不得将多进程 CPU 时间相加伪装为全机吞吐。
5. 单笔 latency、整批 wall-clock、调用方 HTTP/RPC 往返和服务端 HDR 必须使用独立列；调用方体验不得替代内部路径。
6. `P100` 只表示测量窗口最坏值；长期尾延时使用 P99/P99.9 与资源归因共同解释，禁止用一次最低值或一次最大值作 SLA 宣传。

## 6. 执行系统标准

### 6.1 `EXEC-BURST`

每个场地适配器必须声明 burst 宽度 `N`、安全容量依据、共同 release 方式和 scope 分配。所有 route、session/API、frame、连接、CPU affinity 与预触页必须在 `G0` 前完成；测量窗口内禁止冷启动、动态建连、懒初始化、同步日志、远程依赖、UI 或无界队列。

每轮必须同时满足：

- `N/N` 结果都为 adapter accepted、确定性本地拒绝或权威 venue throttle 三者之一；不得出现未解释结果；
- 对被 accepted 的样本，全部拥有完整 `G0→G4` 和 `G5→G7` 时间对，`gap=0`，producer/dispatch/callback error 为零；
- 所有对外副作用在测量窗口外受控清理，terminal callback 与权威未完成查询均闭合；
- 若任一 `G5~G7` 不完整，输出每阶段覆盖计数、首个不完整边界和固定脱敏分类；该轮为 `FAIL`，不得以部分样本重算。

burst 必须输出三项整批墙钟，且仅在全量样本共享同一 release、终点完整时有效：

| 指标 | 公式 |
| --- | --- |
| 提交批次完成 | `shared release → last G4` |
| 全链路批次完成 | `shared release → last G7` |
| callback drain | `first G5 → last G7` |

### 6.2 `EXEC-HOT`

预热后每次只允许一笔从 `G0` 到 `G7` 在途。每笔完整 callback 与清理闭环后才释放下一笔。默认最少 100 笔，输出全部相邻区间、累计区间、P50/P95/P99/P100 和原始配对时间戳。它只代表低并发体验，不能与 burst 排队延时混算。

### 6.3 `EXEC-OVERLOAD`

负载必须超过已经证明的安全接纳容量。每个输入恰好落入 adapter accepted、确定性本地 backpressure 或权威 venue throttle 之一；不得无界排队、重复原生调用、静默丢失、未知 credit 自动释放或未解释 callback gap。恢复后必须执行权威查询与清理，再恢复新单能力。

## 7. OMS 标准 `OMS-W0~W6`

OMS 是已提交执行事实的异步投影。其 CPU、锁、I/O、projector、snapshot publish 和 HTTP 服务不得进入 `G0~G7`。事实源必须可重放、可校验并暴露 position/watermark。

| Gate | 负载与时长 | 强制成功条件 |
| --- | --- | --- |
| `W0` | 环境/contract preflight | schema、fixed seed、CPU shard、HDR、reset、V0~V5 适用项通过；无场地 mutation |
| `W1` | fact-ingest，2,000 TPS，30 s | 完成量达标、零 dropped/HTTP failure，receipt 与 projected 一致 |
| `W2` | immutable snapshot query，5,000 QPS，30 s | 完成量达标、零 dropped/failure，固定 generation snapshot 合法 |
| `W3` | W1+W2 同时，30 s | 两流均达标、零 dropped/failure，固定 seed reset 后执行 |
| `W4` | watermark/health，250 QPS，30 s | health、queue、watermark、pause/stale 一致，零失败 |
| `W5` | admission/queue/freshness fail-closed | pause、硬水位、stale 和非法请求确定性拒绝，绝不错误成功 |
| `W6` | replay/projector pause/stale/resume | replay 等价；暂停 fail-closed；追平后 watermark/snapshot 一致；不反压 `G0~G7` |

W1/W2/W3 的 HTTP/RPC 完整往返与服务端 HDR 必须分开报告。任何 snapshot materialize/publish 都是旁路，不能算入交易热路径。

## 8. EMS 标准 `EMS-E0~E5`

EMS 只衡量策略目标或执行计划在不访问场地时完成有界接纳、路由和 child instruction 准备的能力。不得为了吞吐跳过风险、ownership、幂等、容量或 `G2` 前的可验证准备事实。

| Gate | 负载与时长 | 被测边界与默认门槛 |
| --- | --- | --- |
| `E0` | 环境/contract preflight | scope、route、risk、ownership、schema、seed、HDR/reset 有效；无场地 mutation |
| `E1` | plan/target，2,000 TPS，30 s | `plan_submit→plan_admitted`；零 dropped/failure/越权/重复 child；P95 ≤ 20 ms，P99 ≤ 60 ms |
| `E2` | query，5,000 QPS，30 s | immutable plan/execution/child 查询；零 dropped/failure；P95 ≤ 10 ms，P99 ≤ 40 ms |
| `E3` | child preparation，2,000 TPS，30 s | `plan_admitted→child_instruction_ready`；唯一 parent/route/epoch；P95 ≤ 20 ms，P99 ≤ 60 ms；止于 `G2/G3` 前 |
| `E4` | control，500 TPS，30 s | pause/resume/cancel-plan/reconcile；幂等且单调；P95 ≤ 20 ms，P99 ≤ 60 ms；场地副作用另按 `EXEC` 验收 |
| `E5` | E1+E2+E3 同时，30 s | 三流均完整、零 dropped/failure；不造成 `G0~G7` 回归 |

每个 EMS evidence 必须包含：`plan_submit_to_admitted_ns`、`plan_admitted_to_child_instruction_ready_ns`、`child_instruction_to_execution_scope_enqueued_ns`、查询与控制延时、merge/child/reject 计数，以及服务端 HDR 与调用方往返。

## 9. 策略消费端标准 `STR-S0~S5`

策略消费端只测 transport、鉴权、反序列化、去重、顺序校验、consumer checkpoint 和 immutable snapshot。不得在窗口内执行策略业务逻辑、模型推理、行情计算、磁盘写入或外部网络请求。

| Gate | 负载与时长 | 被测边界与默认门槛 |
| --- | --- | --- |
| `S0` | 环境/contract preflight | ACL、subscription/filter、checkpoint、schema 和 seed 有效；从已确认 position 启动 |
| `S1` | signal submit，2,000 TPS，30 s | `strategy_signal_submit→EMS admitted`；零 dropped/failure；幂等冲突确定性拒绝；P95 ≤ 20 ms，P99 ≤ 60 ms |
| `S2` | event consume，5,000 event TPS，30 s | `G7/S0→consumer receive→checkpoint applied`；零 gap、未解释重复和 scope 内乱序；P95 ≤ 10 ms，P99 ≤ 40 ms |
| `S3` | snapshot/query，5,000 QPS，30 s | `strategy_query→immutable response`；零 dropped/failure；P95 ≤ 10 ms，P99 ≤ 40 ms；包含 generation/watermark/stale |
| `S4` | restart/replay/slow consumer | 无重复副作用、无静默跳读；硬水位明确 backpressure 或停止新订阅 |
| `S5` | S1+S2+S3 同时，30 s | 三流完整；S2 顺序/去重/重放正确；不使 EMS 或执行路径回归 |

`S2` 的分子只能是策略已收到且 checkpoint/state apply 完成的事件，不能以 producer 写入、socket 字节数或 broker callback 数替代。合成 event 容量必须明确标为 synthetic/local，不能冒充 native callback 能力。

## 10. 热路径容量 `H1~H3`

| Workload | 测量边界和分子 | 单位 | 不代表 |
| --- | --- | --- | --- |
| `H1-SIGNAL` | 策略信号完成授权、幂等和 EMS admission | TPS | adapter accepted 或场地受理 |
| `H2-EVENT` | `G7` 等价 outcome 到 consumer receive、checkpoint/state apply | event TPS | callback 数、网络字节或 producer 写入 |
| `H3-QUERY` | 调用方完整 immutable snapshot/query 请求与响应 | QPS | 内存 map lookup 或场地同步查询 |

容量测量规则：

1. 固定 Git、driver、shard、CPU、`RLIMIT_NOFILE`、seed、GC、generator 与 warmup 后，每个 offered rate 独立 reset，运行至少 30 秒 steady plateau。
2. 先按 1.5–2 倍几何加档，接近边界后以不超过 10% 步长夹逼；每档执行均匀和热点 key/scope 两种数据分布。
3. stable plateau 必须同时满足：目标完整生成、零 dropped/failure、业务 receipt/checkpoint 完整、P95/P99/P99.9（适用时）通过、无无界队列或未解释 lag。
4. 可持续上限是最高 stable offered rate，且在同环境独立三轮均稳定；必须同时报告实际 TPS/QPS、分位数、服务端 HDR、资源、队列高水位和数据分布。
5. 首个失稳点是首次出现 dropped、失败、完整性错误、延时违约或无界积压的档位。它只形成 `[可持续上限, 首个失稳 rate]` 边界。
6. 如最高已测档仍稳定，只能报告 `>= highest tested rate`。只有存在服务端有界 admission 的明确拒绝档，才可报告硬容量边界。

## 11. 稳定性与运行中故障 `STAB-L1~L2`

短时 30/60 秒合同不能代替稳定性证明。需要发布候选、容量声明或长期运行承诺的项目必须完成下表。

| Gate | 负载 | 时长 | 通过条件 |
| --- | --- | --- | --- |
| `STAB-L1` | 各项目核心混合合同：OMS W3、EMS E5、策略 S5 或声明的等价组合 | 15 min | 零 dropped/failure、无无界 lag、P95/P99/P99.9 合同通过、资源无持续恶化 |
| `STAB-L2` | `STAB-L1` 混合负载，叠加固定周期 burst 与受控恢复 | 30 min | 所有 burst 后恢复到基线水位；无泄漏、无 queue 漂移、无未解释重试或重复副作用 |

以下故障至少有一次发生在活跃负载期间；每项都必须保存注入点、检测、fail-closed、恢复和权威对账证据：

| 类别 | 最少场景 |
| --- | --- |
| 进程/副作用边界 | `G2` 前、`G3/G4` 周围、`G6` 前终止；未知调用只对账，不自动重报 |
| 存储/资源 | durable frame 半写、校验失败、满盘/`ENOSPC`、慢盘、内存或 cgroup OOM、FD/连接耗尽 |
| 队列/消费者 | ingress/ring 硬水位、projector pause、慢 consumer、checkpoint restart/replay |
| 网络/场地 | 连接 reset、延迟、丢包、短暂不可达、SDK disconnect/relogin、venue throttle |
| 数据语义 | 重复、乱序、迟到 query、热点 key、最大 payload、幂等冲突和非法输入 |

每个故障后的恢复必须证明：无重复外部副作用、无伪造 `G7`、无静默丢失、已知前缀可读、未知 in-flight 保持 `RECONCILE_REQUIRED`，并由权威查询或已声明的权威回放完成核验。权威 API 未提供可验证终态或可关联回放时，不得用本地猜测替代恢复成功。

## 12. 联合无干扰标准 `W7`

`W7` 验证 OMS、EMS 和策略旁路压力不会破坏真实执行完整性。执行、旁路和 generator 必须进程隔离或采用可证明的等价资源隔离；旁路不可写入 `G2/G6` 原始事实 writer。

| 组成 | 最低合同 |
| --- | --- |
| 执行 | 本项目 `EXEC-BURST` 完整通过，包含 callback、清理和权威未完成项为零 |
| OMS | W1 2,000 TPS + W2 5,000 QPS，运行至少 60 s |
| EMS/策略（已实现时） | E1/S1 共用同一 2,000 TPS 输入流；E2/S3 5,000 QPS；E3 2,000 TPS；S2 5,000 event TPS |
| 成功 | 每个子合同独立完整、零 dropped/failure、执行 callback gap 为零、无未解释指令或订单 |

报告必须分别列出 execution、OMS、EMS 和策略的表格。没有同 profile 的交错 control/candidate，不得从一次 W7 运行声称绝对延时提升。

## 13. HA/DR 声称门禁 `DR-H0~H4`

此节只适用于项目明确宣称跨主机 HA、自动恢复或 RPO/RTO。未完成本节的项目必须在报告中明确为单机或 `DISARMED`，不得以 mmap、缓存、备份或进程重启推断 HA。

| Gate | 必须证明的事实 |
| --- | --- |
| `DR-H0` | 书面声明 RPO、RTO、权威事实源、复制确认点、fence 和脑裂处理 |
| `DR-H1` | active 进程故障切换后，不重复执行 `G3/G4` 副作用；未知 in-flight 进入权威对账 |
| `DR-H2` | 主机、网络或存储故障下，复制位置、恢复 watermark 和声明 RPO 一致 |
| `DR-H3` | 切换期间 admission、读写、策略 consumer 和外部回调均遵循已声明的 fail-closed 语义 |
| `DR-H4` | 完整故障恢复后，与权威场地/账本按稳定 client identity、scope 和策略归属双向核对，RTO 内收敛 |

## 14. 通过语义、清理与报告

| 状态 | 含义 |
| --- | --- |
| `PASS` | 全部前置、完整性、延时、吞吐、资源、清理和适用 fault 条件均满足 |
| `FAIL` | 已开始的有效运行违反任一合同；必须保留全部证据，不得重算掩盖 |
| `BLOCKED` | V0~V5、权限、权威查询或环境窗口不具备；没有形成有效性能样本 |
| `EXPLORATORY` | profile、数据、generator 或环境不满足定档条件；只能用于诊断，不得用于回归/发布 |

每次运行必须输出版本化 JSON evidence 与 Markdown 摘要；归档路径固定为：

```text
artifacts/performance/<profile_id>/<YYYY-MM-DD>/<run_id>/
```

摘要至少包含：

```text
system_id / adapter_id / venue_id / environment / run_id / profile_id / schema_version
Git commit / clean state / driver hash / order-plan or fixture hash / seed
host + runtime + SDK/ABI/protocol + capability hash + topology + CPU plan + GC

V0~V5 / preflight / cleanup / authority-query result
per-run all-stage count/P50/P95/P99/P99.9(if applicable)/P100

```

任何对外副作用的 profile 必须在窗口外受控清理。仅“撤单调用被接收”不等于清理成功；必须同时具备 terminal callback（适用时）和权威未完成订单/指令为零。若权威查询语义未被供应商证明，状态必须保持 `RECONCILE_REQUIRED`。

## 15. TradeCore/EMT 定档 profile

本节是 TradeCore/EMT 的精确实现映射；它是统一口径的参考，不是其他项目必须复制的实现。

### 15.1 C0--C7 映射

| 标记 | 真实边界 |
| --- | --- |
| `C0_INGRESS` | 共同 release 后该笔真正进入 TradeCore ingress |
| `C0A_AFTER_INGRESS_DECISION` | admission 接纳并进入 native scheduler |
| `C0B_AFTER_NATIVE_DEQUEUE` | owner native worker 从有界队列取出 |
| `C0C_BEFORE_NATIVE_DISPATCH` | lane/plan/context 准备完成 |
| `C1_BEFORE_ADAPTER` | prepared-route proof 已取得，即将进入 adapter |
| `C1M0/C1M1` | `PRE_NATIVE` mmap frame commit 前/后 |
| `C2_AFTER_PRE_NATIVE_MMAP_COMMIT` | 完整 PRE_NATIVE frame 的 body、CRC、commit word 已提交 |
| `C3_BEFORE_SDK` | 即将调用 EMT `InsertOrder()` |
| `C4_AFTER_SDK` | EMT `InsertOrder()` 同步返回 |
| `C4A_AFTER_ACCEPTED_JOURNAL` | accepted identity/mapping 本地事实完成 |
| `C5_CALLBACK_INGRESS` | EMT 原生 callback 首次进入 TradeCore 观察点 |
| `C5D` | Python callback observer 第一条指令开始 |
| `C5E` | sealed owner route 查表与目标事件重建完成 |
| `C5A` | control profile 的目标 SPSC callback lane 已发布；direct-candidate 必须明确标为 scope-local direct handoff |
| `C5B/C5B2/C5B3` | callback worker 开始、route-state 校验后、frame hash 后 |
| `C5M0/C5M1` | callback mmap frame commit 前/后 |
| `C6_AFTER_CALLBACK_MMAP_COMMIT` | outcome/cancel frame 与本地状态证明完成 |
| `C7_AFTER_DOWNSTREAM` | durable callback 后下游 receipt 完成 |

强制输出相邻与累计项：`C0→C0A`、`C0A→C0B`、`C0B→C0C`、`C0C→C1`、`C1M0→C1M1`、`C1→C2`、`C2→C3`、`C3→C4`、`C4→C4A`、`C0→C4A`、`C5→C5D`、`C5D→C5E`、`C5E→C5A`、`C5A→C5B`、`C5B→C5B2`、`C5B2→C5B3`、`C5B3→C5M0`、`C5M0→C5M1`、`C5M1→C6`、`C6→C7`、`C5→C7` 与直接测得的 `C0→C7`。

`C4→C5` 只能标记为 EMT 外部异步等待。每个相邻 `C5~C7` 阶段必须全量单调配对；缺失任意一对即 `complete=false`。

### 15.2 `TC-EMT-499`

- EMT 已知同时受理上限为每秒 500 笔，标准 burst 为 499 笔共同 release；不创建 499 个线程。
- 使用预热的 process-isolated scope：每 scope 独立 Python 进程、EMT API/session、mmap Journal 与 callback worker；单一 session 内只允许一个 serial native caller。
- 每轮前通过 `V4-CALLBACK`；route、fixed frame、mmap 预触页、CPU affinity 和 order-plan 均在 C0 前完成。
- 运行三轮独立 `499` burst。每轮均须 `499/499` native accepted、C7、完整 `C5→C7` 时间对、zero callback gap、zero producer/dispatch/callback error、受控撤单 terminal callback 及权威未完成订单为零。
- `C1M0→C1M1`：每轮 P99 ≤ 1 ms、P100 ≤ 3 ms；`C5A→C5B`：P95 ≤ 30 ms、P99 ≤ 50 ms；`C5→C7`：P50 ≤ 15 ms、P95 ≤ 40 ms、P99 ≤ 60 ms、P100 ≤ 80 ms。
- `C0→C4A` 仅与同 profile 的冻结 control 比较，P95 不得恶化超过 `max(5 ms, 15%)`；`C3→C4` 和 `C0→C7` 只直接报告，不作为项目内部延时承诺。
- 报单窗口外至少等待 1.1 秒，再以每笔至少 5 ms 的节奏撤单；撤单不计入 C0--C7。

### 15.3 `TC-EMT-HOT-100` 与超载

`TC-EMT-HOT-100` 在 session/API/worker 预热后运行 100 笔，任一时刻只有一笔 `C0→C7` 在途，逐笔完整 callback 与清理后才释放下一笔。它遵循第 6.2 节。超过 499 或场地已批准阈值的输入按 `EXEC-OVERLOAD`，不得冒充为 499 性能结果。

### 15.4 `TC-EMT-499-DIRECT-CANDIDATE`

该 profile 是 callback 旁路的受控 A/B 候选，不是 `TC-EMT-499` 的静默替代：必须为 `DISARMED` 模拟盘、每 scope 独立进程、每 scope 一个 EMT API/session、sealed route、source scope 与 target scope 相同、一个 callback drain writer、有限下游 capture，以及预分配可用的 callback mmap Journal。它始终在 adapter drain worker 中写入，绝不在 SDK 原生回调线程中写入。

候选 profile 保留相同的 `C5→C7` 时间点以便对比；其中 `C5A` 的含义改为“sealed route 后的 scope-local direct handoff”，而非 SPSC publish。任何一项静态证明不足、callback gap、frame 容量不足或跨 scope route 都必须启动失败；不得回退成 control 却把结果标为 candidate。其通过仅证明该候选组成在模拟环境的事实，是否取代 control 仍须在每轮完整 callback 和三轮 A/B evidence 后单独决策。
